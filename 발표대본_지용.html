Q&A 예상 질문 & 답변

Q1. "왜 GPT가 아니라 sLLM을 선택했나요?"

"저희 프로젝트의 핵심 배경이 '사내규정'이라 보안이 중요합니다. GPT를 쓰면 규정 데이터가 외부로 전송되는데, sLLM은 자체 서버에서 돌리니까 프라이버시가 보장됩니다. 비용도 0원이고, API 장애 의존도 없습니다."

Q2. "Base 모델 한계 예시가 실제 돌린 건가요?"

"평가 결과를 기반으로 재구성한 예시입니다. 실제 평가 수치 — 정확도 37.2%, False Fill 44.3%, 분류 유효율 85% — 는 eval 데이터셋으로 측정한 진짜 수치입니다."

Q3. "RAG에 HyDE를 쓴 이유는?"

"사용자가 구어체로 질문하면 BM25가 매칭을 못 합니다. '연차 며칠?'이랑 '유급휴가 부여 일수'는 단어가 다르니까요. HyDE가 LLM으로 가설 문서를 먼저 만들어서 시멘틱 갭을 메워줍니다."

Q4. "Conditional 78%를 어떻게 올릴 계획인가요?"

"Conditional은 yes와 no의 경계에 있는 케이스라 라벨 자체가 모호합니다. 라벨 재정의와 경계 사례 데이터를 집중 보강해서 85%까지 올리는 게 목표입니다."

Q5. "문서요약 파인튜닝 효과가 소폭인데, 왜 필요했나요?"

"좋은 질문입니다. 요약 품질 자체는 Base도 괜찮았어요. 하지만 문서관리 페이지에서 분류 필터, 태그 검색, 미리보기가 동작하려면 출력 포맷이 일관되어야 합니다. Base는 15%가 잘못된 카테고리를 만들어서 필터가 깨졌고, 파인튜닝으로 서비스 안정성을 확보한 겁니다."

Q6. "커스텀 템플릿이 복잡한 표를 못 다루면 어떻게 하나요?"

"현재 Placeholder 방식은 라벨-빈칸 패턴을 감지하는 방식이라 단순한 표는 잘 되지만, 병합된 셀이나 중첩 표는 어렵습니다. 향후에는 파인튜닝 데이터를 다양한 문서 양식 기반으로 학습시켜서 더 많은 양식을 지원할 계획입니다."

Q7. "RAG 학습에 넣으면 왜 오히려 성능이 떨어졌나요?"

"RAG 검색 결과에 노이즈가 섞여 있어서, 학습 데이터의 라벨과 모순이 생겼습니다. 예를 들어 정답은 'yes'인데 RAG가 가져온 규정이 관련 없는 조항이면 모델이 혼란을 느끼는 거죠. 그래서 학습할 때는 하드코딩으로 깨끗한 신호를 주고, 실제 서빙할 때만 RAG를 쓰는 전략으로 바꿨습니다."
