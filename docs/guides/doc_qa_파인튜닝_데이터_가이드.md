# doc_qa 파인튜닝 데이터 완전 가이드

## 1. doc_qa란?

사용자가 **팀 내부 업무 문서**(회의록, 보고서, 기획서)에서 답을 찾는 질문을 했을 때, RAG 검색 결과를 기반으로 **답변 + 출처 인용**을 생성하는 기능.

> 예: "지난주 마케팅 회의에서 예산 얼마로 정했어?"

규정 문서가 아닌 **비규정 업무 문서**가 대상 (regulation_qa와의 차이점).

---

## 2. 프로덕션 실제 동작 흐름

```
사용자: "마케팅 예산 얼마야?"
         │
         ▼
   ┌─────────────┐
   │ Intent 분류  │ → "doc_search" (문서 검색 의도)
   └─────┬───────┘
         ▼
   ┌─────────────┐
   │  RAG 검색    │ → Qdrant에서 사용자가 업로드한 문서들 중
   │             │    관련 문서 조각(chunks) 3~5개 검색
   └─────┬───────┘
         ▼
   검색 결과 예시:
   [1] (마케팅_주간회의_0220.md) "SNS 마케팅 예산 500만원 승인..."
   [2] (2분기_기획서.md) "2분기 마케팅 예산 총 2000만원..."
   [3] (팀장_업무보고_0215.md) "전분기 마케팅 예산 1500만원 집행..."
         │
         ▼
   ┌─────────────┐
   │   LLM 호출   │ ← 질문 + 위 chunks 3개를 같이 넣음
   └─────┬───────┘
         ▼
   LLM 출력:
   {
     "answer": "SNS 마케팅 예산 500만원이 승인되었고,
                2분기 전체 예산은 2000만원입니다.",
     "citations": [
       {"source": "마케팅_주간회의_0220.md",
        "content": "SNS 마케팅 예산 500만원 승인",
        "relevance": "높음"},
       {"source": "2분기_기획서.md",
        "content": "2분기 마케팅 예산 총 2000만원",
        "relevance": "보통"}
     ],
     "confidence": 0.9
   }
```

## 3. 왜 파인튜닝이 필요한가?

| 상태 | 설명 |
|------|------|
| **현재** | GPT/Claude API가 위 작업을 해줌 (비쌈, 외부 의존) |
| **목표** | 자체 sLLM(A.X 기반)이 이걸 하게 하고 싶음 |
| **문제** | A.X는 범용 모델이라 citations 포함 답변 형식을 잘 못 맞춤 |
| **해결** | 이 패턴의 예시 데이터 200~500개를 보여주고 학습(LoRA)시킴 |

---

## 4. 파인튜닝 데이터 1쌍의 구조

모델에게 가르치는 건 **"이런 입력이 오면 이런 출력을 내라"**:

```json
{
  "instruction": "업무 문서 컨텍스트를 참고하여 질문에 답변하고, 인용 출처를 반드시 포함하세요.",
  "input": "[질문]\n마케팅 예산 얼마야?\n\n[컨텍스트]\n[1] (마케팅_주간회의_0220.md) SNS 마케팅 예산 500만원 승인...\n[2] (2분기_기획서.md) 2분기 마케팅 예산 총 2000만원...\n[3] (팀장_업무보고_0215.md) 전분기 예산 1500만원 집행...",
  "output": "{\"answer\": \"SNS 마케팅 예산 500만원이 승인...\", \"citations\": [...], \"confidence\": 0.9}"
}
```

### 각 필드 설명

| 필드 | 역할 | 비유 |
|------|------|------|
| `instruction` | 모든 샘플에 동일한 시스템 프롬프트 | "너는 문서 QA 봇이야" |
| `input` | 질문 + RAG 검색 결과 (매번 다름) | 시험 문제 |
| `output` | 정답 + 인용 출처 (매번 다름) | 모범 답안 |

**주의: instruction은 사용자 질문이 아님!** 모델에게 주는 지시사항이고, 모든 500개 데이터에 동일하게 들어감. 사용자 질문은 `input`의 `[질문]` 부분에 들어감.

### 프로덕션 매핑

```
프로덕션 동작                    학습 데이터 필드
──────────────                  ─────────────
시스템 프롬프트 설정        →    instruction (고정)
사용자가 질문 입력         →    input의 [질문] 부분
RAG가 문서 검색            →    input의 [컨텍스트] 부분
LLM이 답변 생성            →    output (이걸 학습시키는 것)
```

---

## 5. citations이 필요한 이유

단순 답변만 하면 사용자가 "이거 진짜야? 어디서 나온 정보야?" 라고 물어봄.

citations이 있으면:
- 답변의 **신뢰성** 확보 (출처 제시)
- 사용자가 **원본 문서**로 바로 이동 가능
- **hallucination 방지** — 컨텍스트에 없는 내용을 지어내면 citations을 달 수 없음

## 6. 팀원 테스트(승언)와의 관계

### 승언이 한 것 (qa_test/) — 베이스라인 모델 비교

```json
// 단순한 구조
{ "id": "gen_001", "domain": "general", "context": "...", "question": "...", "answer": "..." }
```

- context 직접 제공 (RAG 없음)
- 출력은 단순 답변 (citations 없음)
- 40개 샘플로 Midm vs A.X 비교 → **A.X 선정됨**
- 약점 보완용 합성 데이터 500개 생성 스크립트도 작성

### doc_qa 스펙 — 파인튜닝용 최종 데이터

```json
// 복잡한 구조
{ "instruction": "...", "input": "질문+chunks", "output": "답변+citations+confidence" }
```

- context가 RAG에서 검색됨
- 출력에 인용 출처(citations) 포함

### 핵심 차이

| | 팀원 테스트 (현재) | doc_qa 스펙 (목표) |
|---|---|---|
| **컨텍스트** | 직접 제공 | RAG 검색 결과 |
| **출력** | 단순 답변 | 답변 + 인용 + 신뢰도 |
| **목적** | 베이스 모델 선정 | 프로덕션용 파인튜닝 |
| **단계** | 모델 비교 (완료) | 4단계 파인튜닝 데이터 |

**승언이 한 건 Step 1 (모델 선정), doc_qa 스펙은 Step 2 (학습 데이터).**

```
[승언이 한 것]                    [앞으로 해야 할 것]

모델 비교 테스트                   파인튜닝 데이터 생성
    │                                  │
    ▼                                  ▼
A.X vs Midm                     A.X에 학습시킬
40개 샘플로 비교                  500개 QA+인용 데이터
    │                                  │
    ▼                                  ▼
A.X 선정! ────────────────────→ 이 모델을 가르치자
    │                                  │
    ▼                                  ▼
약점 분석                         약점 보완 데이터 포함
(multi_entity 혼동,               (citations 형식 학습,
 열거 누락 등)                     정확한 인용 등)
```

## 7. 데이터 수집 방법

```
방법 1: LLM으로 생성 (주력)
─────────────────────────
1. 샘플 업무 문서들 준비 (회의록, 보고서 등)
2. 문서를 chunks로 나눔
3. GPT/Claude에게: "이 문서에서 나올 수 있는 질문 만들어줘"
4. 생성된 질문 + chunks → GPT/Claude에게: "답변 + citations 만들어줘"
5. 검수: citations에 있는 내용이 실제 chunks에 있는지 확인

방법 2: 실제 사용 로그 (보조)
─────────────────────────
1. 프로덕션에서 사용자가 실제로 한 질문 (chat_logs)
2. RAG 검색 결과 + GPT 답변을 기록해둠
3. 검수 후 학습 데이터로 활용

방법 3: 수동 생성 (품질 보완)
─────────────────────────
1. 엣지 케이스 직접 작성 (context에 답이 없는 경우 등)
```

## 8. Chat Format (대화 형식 변환)

### 누가 정하나?

**모델을 만든 사람(모델 제작사)이 정해둔 것.** 우리가 정하는 게 아님.

### 모델마다 다른 Chat Format 예시

**A.X (SKT):**
```
<|im_start|>system
업무 문서 컨텍스트를 참고하여 답변하세요.<|im_end|>
<|im_start|>user
마케팅 예산 얼마야?<|im_end|>
<|im_start|>assistant
SNS 마케팅 예산 500만원입니다.<|im_end|>
```

**Llama 계열:**
```
<s>[INST] <<SYS>>
시스템 프롬프트
<</SYS>>

사용자 질문 [/INST] 모델 답변 </s>
```

**ChatGPT 계열:**
```json
{"role": "system", "content": "..."}
{"role": "user", "content": "..."}
{"role": "assistant", "content": "..."}
```

### 실제로 어떻게 적용하나?

```python
# 1. 우리는 이렇게만 준비하면 됨 (모델 무관한 표준 형식)
messages = [
    {"role": "system", "content": "instruction 내용"},
    {"role": "user", "content": "input 내용"},
    {"role": "assistant", "content": "output 내용"}
]

# 2. tokenizer가 모델에 맞는 형식으로 자동 변환
formatted = tokenizer.apply_chat_template(messages)
# → <|im_start|>system\n...<|im_end|>\n... (자동)
```

## 9. 파인튜닝 데이터 형식은 "정해진" 것이 아닌 "관례"

### 널리 쓰이는 형식들

```
1. Alpaca 형식 (가장 흔함) ← 우리 doc_qa가 이걸 따름
   {"instruction": "...", "input": "...", "output": "..."}

2. ShareGPT/Chat 형식
   {"messages": [{"role": "system", ...}, {"role": "user", ...}, {"role": "assistant", ...}]}

3. 단순 분류 형식 ← Intent 분류가 이걸 따름
   {"text": "...", "label": "..."}

4. 완전 자유 형식
   {"prompt": "...", "completion": "..."}
```

### 학습 프레임워크별 지원 형식

| 프레임워크 | 주로 쓰는 형식 |
|-----------|--------------|
| Hugging Face SFTTrainer | Alpaca, Chat |
| Axolotl | Alpaca, ShareGPT, 커스텀 |
| LLaMA-Factory | Alpaca, ShareGPT |
| OpenAI Fine-tuning | `{"messages": [...]}` |

**핵심: 데이터의 "형식"보다 "내용의 품질"이 훨씬 중요.** 형식은 변환 스크립트로 바꿀 수 있지만, 질문-답변 쌍의 품질은 처음부터 잘 만들어야 함.

## 10. Intent vs doc_qa: 왜 데이터 형식이 다른가

### Intent 분류 = "분류" 문제 (객관식 시험)

```json
{"text": "이거 규정 위반이야?", "label": "judgment"}
```

모델이 할 일: **7개 중 하나 고르기** → 정답이 단어 하나

### doc_qa = "생성" 문제 (서술형 시험)

```json
{"instruction": "...", "input": "질문+chunks", "output": "답변+citations+confidence"}
```

모델이 할 일: **문장을 만들어내기** → 정답이 문장 + 구조화된 JSON

### 비교

| 태스크 | 하는 일 | 입력 | 출력 | 데이터 형식 |
|--------|--------|------|------|------------|
| Intent | 분류 | 문장 1개 | 라벨 1개 | `{text, label}` |
| doc_qa | 답변 생성 | 질문+문서조각 | 답변+인용 | `{instruction, input, output}` |
| regulation_qa | 규정 답변 | 질문+규정조항 | 답변+근거 | `{instruction, input, output}` |
| doc_generate | 문서 생성 | 요청사항 | 완성된 문서 | `{instruction, input, output}` |

**파인튜닝 데이터 형식 = 모델이 실제로 할 일의 입출력 형태.**
분류 태스크는 `{text, label}`로 충분하고, 생성 태스크는 `{instruction, input, output}`이 필요.

## 11. 파인튜닝이 학습하는 것

**형식만 학습하는 게 아니라 "능력"을 학습:**

| 학습 대상 | 비유 | 중요도 |
|-----------|------|--------|
| JSON 출력 형식 | 답안지 양식 맞추기 | 20% |
| **컨텍스트에서 정답 찾기** | **독해 능력** | **40%** |
| **정확한 출처 연결하기** | **근거 제시 능력** | **30%** |
| **없는 내용 안 지어내기** | **hallucination 억제** | **10%** |

예시:
```
[컨텍스트]
[1] (회의록.md) 예산 500만원 승인
[2] (기획서.md) 인력 3명 배정
[3] (보고서.md) 매출 10억 달성

[질문] 예산 얼마야?
```

모델이 학습하는 건:
- 3개 중에서 **[1]이 관련 있다**는 판단력
- [2], [3]은 **무시하는 능력**
- "500만원"을 답하면서 **[1]을 인용하는 연결력**
- 기획서에 있는 "3명"을 예산이라고 **지어내지 않는 것**

형식은 1~2시간이면 학습되지만, 위 능력들은 데이터 품질과 양이 충분해야 제대로 학습됨. 그래서 200~500쌍이 필요.

## 12. JSON 생성 후 → 배포까지 전체 파이프라인

```
[ STEP 0 ] 모델 선정 ✅ 완료
──────────────────────
  Midm vs A.X 비교 → A.X-3.1-Light 선정 (승언 완료)


[ STEP 1 ] 파인튜닝 데이터 생성 ← 지금 여기
──────────────────────────────
  업무 문서 (회의록, 보고서 등)
       │
       ▼
  GPT/Claude로 질문 생성
       │
       ▼
  질문 + 문서 chunks → GPT/Claude로 답변+인용 생성
       │
       ▼
  검수 (인용이 실제 context에 있는지)
       │
       ▼
  ft_train_data.json (500쌍)
  { "instruction": "고정",
    "input": "질문+chunks",
    "output": "답변+인용" }


[ STEP 2 ] 데이터 변환
──────────────────────
  JSON → chat messages 형식

  { "instruction": "...",        { "messages": [
    "input": "...",        →       {"role": "system", ...},
    "output": "..." }              {"role": "user", ...},
                                   {"role": "assistant", ...}
                                 ]}

  tokenizer.apply_chat_template()가
  모델별 특수 토큰 자동 추가


[ STEP 3 ] LoRA 학습 (RunPod A100)
──────────────────────────────────
  A.X 원본 (7B, 수십GB) ← 건드리지 않음
       +
  LoRA 어댑터 (~1%, 수십MB) ← 이것만 학습

  500개 데이터로 1~2시간 학습
       │
       ▼
  adapter_model/ 파일 생성


[ STEP 4 ] 평가
──────────────
  테스트 데이터 50~100개로 확인

  측정 항목:
  - Token F1 (답변 정확도)
  - Citations 정확도 (인용이 맞는지)
  - 형식 준수율 (JSON 출력이 깨지지 않는지)

  통과? → STEP 5로
  실패? → STEP 1로 돌아가 데이터 보강 후 재학습


[ STEP 5 ] vLLM 배포
────────────────────
  A.X + LoRA 어댑터 → vLLM 서버에 로드

  OpenAI 호환 API 제공:
  POST http://서버:8000/v1/completions


[ STEP 6 ] 코드 교체 (1줄)
─────────────────────────
  기존:  base_url = "https://api.openai.com/v1"
  변경:  base_url = "http://our-server:8000/v1"

  나머지 코드는 동일!
  (vLLM이 OpenAI 호환 API를 제공하기 때문)
```

### 전체 요약

```
[지금]                [4단계]                    [프로덕션]

JSON 데이터 생성  →  LoRA 학습  →  평가  →  vLLM 배포  →  서비스
  500쌍              A100 1~2h     테스트     API 서버      사용자
                                   통과?
                                   No → 데이터 보강 후 재학습
                                   Yes → 배포!

결과: 외부 API 비용 없이 자체 doc_qa 모델 운영
```
