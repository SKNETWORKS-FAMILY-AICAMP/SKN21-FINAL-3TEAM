## 슬라이드 1: 프로젝트 소개 (1분)

안녕하세요. WorkFlow Agent, 저희가 "듀듀"라고 부르는 프로젝트를 소개하겠습니다.

듀듀는 **LangGraph 기반 멀티 Agent 업무 자동화 시스템**입니다. 사내 규정 판단, 문서 분석과 생성, 일정 관리를 AI Agent가 처리합니다.

대상 사용자는 **사내 직원**입니다. 챗봇에 "이거 규정 위반이야?", "보고서 작성해줘", "내일 3시 회의 잡아줘" 같이 자연어로 요청하면, 시스템이 의도를 파악해서 적절한 Agent로 연결하고, 결과를 돌려주는 구조입니다.

핵심 기능은 크게 4가지입니다:
1. **규정 판단** — RAG로 사내 규정 검색 후 AI가 판단
2. **문서 관리** — 검색, 생성, 요약, Q&A
3. **일정 관리** — Google Calendar 연동, 자연어로 등록/조회
4. **회의록 생성** — 회의 내용 입력하면 자동 정리

---

## 슬라이드 2: 전체 아키텍처 (1분)

전체 아키텍처입니다.

사용자 입력이 들어오면 **오케스트레이터**가 가장 먼저 받습니다. 오케스트레이터 안에 **Intent Classifier**가 있어서 입력을 8개 의도 중 하나로 분류합니다. 그 결과에 따라 4개 Agent 중 하나로 라우팅합니다.

```
사용자 입력
  → Intent Classifier (KoELECTRA, 7.9ms)
    → 8개 intent 분류
      → Judgment Agent (규정 판단, RAG + Qdrant)
      → Document Agent (문서 검색/생성/요약/Q&A)
      → Schedule Agent (일정 등록/조회, Google Services)
      → General Handler (일상 대화)
```

여기서 핵심이 **Intent Classifier**입니다. 잘못 분류하면 엉뚱한 Agent로 가니까 잘못된 답변이 나옵니다. 그래서 이 분류기의 정확도가 전체 시스템 품질을 결정합니다.

기술 스택은 Backend가 FastAPI + SSE, Frontend가 React + Zustand, AI가 LangGraph + Qdrant, 인프라가 AWS EC2 + GitHub Actions CI/CD입니다.

## 슬라이드 3: 핵심 기능 시연 (2분)

실제 화면을 보여드리겠습니다.

**(1) 규정 판단** — "인턴에게 AWS 접근 권한 줘도 돼?"라고 물으면, Intent Classifier가 judgment로 분류하고, RAG가 사내 규정 270개 청크에서 관련 조항을 검색하고, Judgment Agent가 근거와 함께 판단 결과를 돌려줍니다. 현재 규정 판단 E2E 테스트 6단계 전부 통과했습니다.

**(2) 일정 관리** — "내일 3시 팀 회의 잡아줘"라고 하면 Google Calendar에 등록되고, Meet 링크도 자동 생성되고, 참석자에게 초대 메일까지 발송됩니다. Google Services 5개(Calendar, Tasks, Gmail, Meet, Sheets)가 통합되어 있습니다.

**(3) 문서 관리** — PDF, DOCX, TXT 파일 업로드하면 텍스트 자동 추출, 목록 조회, 상세 보기가 됩니다.

**(4) 부가 기능** — 다크모드, 인쇄, 대시보드 위젯 자유 배치, 대화 세션 관리 등이 구현되어 있습니다.

> 문서 생성과 회의록 생성은 Document Agent 고도화 진행 중이라 다음 발표에서 시연하겠습니다.

## 슬라이드 4: 팀 진행 현황 (1분)

팀 진행 현황입니다. 5명이 역할을 나눠서 진행하고 있습니다.

| 담당 | 이름 | 핵심 완료 사항 | 구현율 |
|------|------|---------------|:------:|
| PM + Intent | 지용 | Intent 분류 6단계 실험 완료, 오케스트레이터 3분기 라우팅 | 95% |
| AI (판단) | 경은 | RAG 파이프라인 + Judgment Agent + E2E 통과 | 90% |
| AI (문서) | 승언 | AWS 배포 + CI/CD 완료, Document Agent 고도화 진행 중 | 50% |
| Backend | 혜빈 | DB 11테이블 + API 46/51개 + Google Services 5종 | 85% |
| Frontend | 지영 | 10페이지 + 63컴포넌트 + 다크모드/인쇄/애니메이션 | 85% |

전체 진행률은 약 **65%**입니다. 1~2단계(설계+기반) 100%, 3단계(Agent) 75%, 6단계(배포) 50% 완료.

**핵심 블로커**는 Document Agent입니다. doc_search, doc_generate, doc_summary, doc_qa 4개 intent가 이 Agent에 의존하고 있어서, 이걸 완성하면 나머지 연동이 순차적으로 풀립니다.

## 슬라이드 5: Intent 분류 — 문제 + 데이터 (1분)

> 차트: `class_distribution.png`

이제 Intent 분류 실험에 대해 설명하겠습니다.

저희 시스템은 8개 intent를 분류합니다. judgment, doc_search, doc_generate, doc_summary, doc_qa, schedule_add, schedule_view, general입니다.

핵심 의사결정이 하나 있었습니다. **이 분류를 GPT 같은 LLM API로 할 것인가, 아니면 파인튜닝한 sLLM으로 할 것인가.** 이전 실험(v1)에서 둘을 비교해봤는데, 정확도는 동급이었지만 속도가 **sLLM이 68배 빠르고 비용이 $0**이었습니다. 매 대화마다 호출되는 작업이라 sLLM을 선택했습니다.

데이터는 GPT-4o와 Claude Sonnet 4, 2개 LLM으로 생성했습니다. 단일 LLM으로 만들면 비슷한 문체가 반복되니까, 2개 LLM이 각각 다른 스타일로 생성하고 서로 교차 검증했습니다.

총 약 **2,900개**입니다. 기본 데이터 2,299개에 혼동 가능한 intent 쌍의 경계 데이터 600개를 합쳤습니다. 8개 클래스가 균형 있게 분포되어 있고, max/min 비율이 1.28배로 양호합니다.

## 슬라이드 6: 모델 비교 + 선택 (1.5분)

> 차트: `baseline_comparison.png`, `f1_vs_speed.png`

3가지 모델을 동일 조건에서 비교했습니다.

| 모델 | 아키텍처 | Val F1 | 추론 속도 |
|------|---------|:------:|:--------:|
| KoELECTRA | ELECTRA (RTD) | **98.25%** | **7.9ms** |
| BERT | BERT (MLM) | 97.80% | 10.4ms |
| DistilKoBERT | DistilBERT | 94.98% | 2.8ms |

Val 데이터에서는 셋 다 높은데, 실전과 비슷한 **적대적 테스트 450문장**으로 평가하니 차이가 벌어집니다. KoELECTRA가 Adversarial F1 **86.04%**로 가장 높았습니다. BERT 85.17%, DistilKoBERT 79.26%였습니다.

속도를 보면 KoELECTRA가 7.9ms로 BERT(10.4ms)보다 24% 빠릅니다. DistilKoBERT는 2.8ms로 가장 빠르지만 정확도가 7%p 낮습니다.

"같은 크기인데 왜 KoELECTRA가 더 좋은가?"에 대한 답은 **사전학습 방식**입니다. BERT는 빈칸 채우기(MLM)로 학습하고, ELECTRA는 토큰 교체를 감지하는 방식(RTD)으로 학습합니다. 짧은 한국어 문장에서 미세한 의미 차이를 구분하는 데 RTD가 유리했습니다.

그래서 **KoELECTRA를 최종 모델로 선택**했습니다.

## 슬라이드 7: 개선 과정 + 최종 결과 (1.5분)

> 차트: `stage6_comparison.png`

선택한 KoELECTRA를 6단계에 걸쳐 개선했습니다. 핵심만 말씀드리겠습니다.

**1단계: 하이퍼파라미터 탐색** — 32가지 조합을 시도했는데, Baseline 대비 +0.72%p밖에 안 올랐습니다. **데이터 품질이 하이퍼파라미터보다 중요하다**는 걸 확인했습니다.

**2단계: 오분류 분석 + 타겟 보강** — 적대적 테스트에서 63건 오분류를 분석했더니, doc_qa(문서 Q&A)가 F1 71%로 가장 약했습니다. doc_search와 경계가 모호해서 헷갈리는 거였습니다. 약한 intent를 타겟으로 **98개만 정밀 보강**했더니 Adversarial F1이 86.04%에서 **87.84%로 +1.8%p** 올랐습니다. doc_qa는 71%에서 **79%로 +8%p** 개선됐습니다.

**3단계: 과신뢰 해소** — 문제가 하나 더 있었습니다. 오분류 63건 중 42건(67%)이 **confidence 90% 이상인데 틀리는 경우**였습니다. 모델이 확신을 갖고 틀리니까 안전장치가 작동하지 않는 거죠. Label Smoothing 0.1을 적용해서 과신뢰 오류를 42건에서 **13건으로 69% 줄였습니다**. F1은 0.26%p만 떨어졌고요.

이제 **confidence 0.85를 기준으로 정답과 오답을 구분**할 수 있게 됐습니다. 0.85 이하면 사용자에게 "혹시 이 중에 원하시는 게 있나요?"라고 되묻는 clarify 라우팅이 작동합니다.

최종 결과: **Adversarial F1 87.58%, 추론 7.9ms, 과신뢰 오류 -69%.**

## 슬라이드 8: 실전 검증 — 시나리오 테스트 (1분)

> 차트: `scenario_test_accuracy.png`

숫자만으로는 실제 서비스에서 잘 되는지 알 수 없으니까, **30문장으로 실제 라우팅 시뮬레이션**을 했습니다. 4가지 유형으로 나눠서 테스트했습니다.

| 유형 | 예시 | 정확도 |
|------|------|:------:|
| 표준 입력 | "이번 달 일정 알려줘" | **7/7 (100%)** |
| 경계 입력 | "휴가 규정에 대해 판단해줄 수 있어?" | 7/8 (87.5%) |
| 비속어/이모티콘 | "그 계약서 검토 좀 해줄래ㅋㅋ" | 6/7 (85.7%) |
| 초단문 (1~2어절) | "문서 질문" | 6/8 (75.0%) |

전체 **26/30 (86.7%)**이고, 오분류 4건 중 3건은 confidence가 0.85 이하라서 clarify 라우팅으로 잡힙니다. 나머지 1건은 라벨 자체가 모호한 경우였습니다.

초단문이 가장 어려운데, 이건 모델의 한계라기보다 정보 자체가 부족한 거라서 clarify로 되묻는 게 올바른 대응입니다.

## 슬라이드 9: 최종 모델 + 향후 계획 (1분)

최종 모델 한 장 요약입니다.

```
모델: KoELECTRA-base-v3 (Full Fine-tuning + Label Smoothing 0.1)
데이터: ~2,900개 (GPT-4o + Claude Sonnet 4)
config: epochs=10, lr=3e-5, batch=16

Val F1:          98.94%
Test F1:         97.88%
Adversarial F1:  87.58% (450문장, 의도적으로 어려운 데이터)
추론 속도:       7.9ms (GPU)
비용:            $0 (로컬 추론)
```

**중간발표 이후 계획**입니다.

| 단계 | 내용 | 기간 |
|------|------|------|
| 3단계 마무리 | Document Agent 완성 (핵심 블로커 해소) | ~이번 주 |
| 4단계 | 데이터 1,400개 수집 + LoRA 파인튜닝 (판단/문서) | 1주 |
| 5단계 | sLLM 교체 + E2E 통합 테스트 + 성능 평가 | 1주 |
| 6단계 | AWS 배포 마무리 + 최종 발표 준비 | 1주 |

코드 구조상 LLM 호출 인터페이스만 바꾸면 되도록 설계해놨기 때문에, 파인튜닝 후 모델 교체는 간단합니다.

## 예상 질문 & 답변 (백업)

**Q1: 왜 BERT가 아니라 KoELECTRA인가요?**

> 동일 크기(111M)에서 KoELECTRA가 Adversarial F1 0.87%p 높고 추론 24% 빠릅니다. 통계적 유의차(McNemar)는 없지만, 속도+강건성에서 우위라서 선택했습니다.

**Q2: Adversarial 87%면 실서비스에서 13%가 틀리나요?**

> Adversarial은 의도적으로 어렵게 만든 데이터입니다. 일반 입력(Val)에서는 98.9%입니다. 그리고 틀리더라도 confidence 0.85 이하면 사용자에게 되묻는 clarify 전략이 있어서 안전하게 처리됩니다.

**Q3: 데이터 2,900개면 적지 않나요?**

> 8개 분류에 카테고리당 ~360개이고, Val F1 98.9%에 도달했습니다. 실험에서 "양보다 품질이 중요하다"는 걸 확인했습니다. 하이퍼파라미터 32가지 조합보다 타겟 보강 98개가 +1.8%p로 훨씬 효과적이었습니다.

**Q4: Label Smoothing으로 F1이 떨어지는데 왜 적용했나요?**

> F1 하락이 -0.26%p로 미미한 반면, 과신뢰 오류가 42건에서 13건으로 69% 줄었습니다. 실서비스에서는 "확신 있게 틀리는 것"이 "살짝 못 맞추는 것"보다 훨씬 위험합니다. threshold 0.85로 정답/오답을 분리할 수 있게 된 것이 핵심 성과입니다.

**Q5: Document Agent 블로커는 언제 해결되나요?**

> 이번 주 내 완성이 목표입니다. Solar API 연동과 State 전달은 확인됐고, RAG 연동과 템플릿 렌더링이 남아 있습니다. 완성되면 Backend AI 연동 → Frontend 교체 순으로 빠르게 통합할 수 있습니다.
