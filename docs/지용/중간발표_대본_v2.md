## 슬라이드 1: 프로젝트 소개 (1분)

안녕하세요. WorkFlow Agent, 저희가 "듀듀"라고 부르는 프로젝트를 소개하겠습니다.

듀듀는 **LangGraph 기반 멀티 Agent 업무 자동화 시스템**입니다. 사내 규정 판단, 문서 분석과 생성, 일정 관리를 AI Agent가 처리합니다.

대상 사용자는 **사내 직원**입니다. 챗봇에 "이거 규정 위반이야?", "보고서 작성해줘", "내일 3시 회의 잡아줘" 같이 자연어로 요청하면, 시스템이 의도를 파악해서 적절한 Agent로 연결하고, 결과를 돌려주는 구조입니다.

핵심 기능은 크게 4가지입니다:
1. **규정 판단** — RAG로 사내 규정 검색 후 AI가 판단
2. **문서 관리** — 검색, 생성, 요약, Q&A
3. **일정 관리** — Google Calendar 연동, 자연어로 등록/조회
4. **회의록 생성** — 회의 내용 입력하면 자동 정리

## 슬라이드 2: 전체 아키텍처 (1분)

전체 아키텍처입니다.

사용자 입력이 들어오면 **오케스트레이터**가 가장 먼저 받습니다. 오케스트레이터 안에 **Intent Classifier**가 있어서 입력을 8개 의도 중 하나로 분류합니다. 그 결과에 따라 4개 Agent 중 하나로 라우팅합니다.

```
사용자 입력
  → Intent Classifier (KoELECTRA, 7.9ms)
    → 8개 intent 분류
      → Judgment Agent (규정 판단, RAG + Qdrant)
      → Document Agent (문서 검색/생성/요약/Q&A)
      → Schedule Agent (일정 등록/조회, Google Services)
      → General Handler (일상 대화)
```

여기서 핵심이 **Intent Classifier**입니다. 잘못 분류하면 엉뚱한 Agent로 가니까 잘못된 답변이 나옵니다. 그래서 이 분류기의 정확도가 전체 시스템 품질을 결정합니다.

기술 스택은 Backend가 FastAPI + SSE, Frontend가 React + Zustand, AI가 LangGraph + Qdrant, 인프라가 AWS EC2 + GitHub Actions CI/CD입니다.

## 슬라이드 3: 핵심 기능 시연 (2분)

실제 화면을 보여드리겠습니다.

**(1) 규정 판단** — "인턴에게 AWS 접근 권한 줘도 돼?"라고 물으면, Intent Classifier가 judgment로 분류하고, RAG가 사내 규정 270개 청크에서 관련 조항을 검색하고, Judgment Agent가 근거와 함께 판단 결과를 돌려줍니다. 현재 규정 판단 E2E 테스트 6단계 전부 통과했습니다.

**(2) 일정 관리** — "내일 3시 팀 회의 잡아줘"라고 하면 Google Calendar에 등록되고, Meet 링크도 자동 생성되고, 참석자에게 초대 메일까지 발송됩니다. Google Services 5개(Calendar, Tasks, Gmail, Meet, Sheets)가 통합되어 있습니다.

**(3) 문서 관리** — Document Agent가 LLM과 연동되어 문서 검색, Q&A, 요약이 동작합니다. PDF, DOCX, TXT 업로드 후 텍스트 자동 추출, 목록 조회, 상세 보기까지 지원됩니다.

**(4) 부가 기능** — 다크모드, 인쇄, 대시보드 위젯 자유 배치, 대화 세션 관리 등이 구현되어 있습니다.

## 슬라이드 4: 팀 진행 현황 (1분)

팀 진행 현황입니다. 5명이 역할을 나눠서 진행하고 있습니다.

| 담당 | 이름 | 핵심 완료 사항 | 구현율 |
|------|------|---------------|:------:|
| PM + Intent | 지용 | Intent 분류 7단계 실험 완료, 오케스트레이터 라우팅 | 95% |
| AI (판단) | 경은 | RAG 파이프라인 + Judgment Agent + E2E 통과 | 90% |
| AI (문서) | 승언 | AWS 배포 + CI/CD 완료, Document Agent LLM 연동 동작 | 70% |
| Backend | 혜빈 | DB 11테이블 + API 46/51개 + Google Services 5종 | 85% |
| Frontend | 지영 | 10페이지 + 63컴포넌트 + 다크모드/인쇄/애니메이션 | 85% |

전체 진행률은 약 **75%**입니다. 설계와 기반 개발은 끝났고, 4개 Agent 모두 LLM API와 연동되어 기본 동작하는 상태입니다.

현재 각 Agent는 **GPT/Claude 같은 LLM API로 동작** 중이고, 중간발표 이후 **sLLM 파인튜닝으로 교체**할 예정입니다. 코드 구조상 LLM 호출 인터페이스만 바꾸면 되도록 설계했기 때문에 교체가 간단합니다.

## 슬라이드 5: Intent 분류 — 문제 정의 (1분)

> 차트: `class_distribution.png`

이제 제가 맡은 Intent 분류 실험에 대해 설명하겠습니다.

**문제는 단순합니다.** 사용자 입력이 들어오면 8개 의도 중 하나로 분류해야 합니다. 잘못 분류하면 엉뚱한 Agent가 답변하니까, 이 분류기가 전체 시스템의 관문입니다.

첫 번째 의사결정: **LLM API vs 파인튜닝 sLLM**. 이전 실험에서 비교했더니 정확도는 동급인데 **sLLM이 68배 빠르고 비용 $0**이었습니다. 매 대화마다 호출되니까 sLLM을 선택했습니다.

데이터는 GPT-4o와 Claude Sonnet 4, 2개 LLM으로 총 **약 2,900개**를 생성했습니다. 단일 LLM이면 문체가 편향되니까 두 모델이 반반씩 생성하고 교차 검증했습니다.

## 슬라이드 6: 모델 비교 + 선택 (1.5분)

> 차트: `baseline_comparison.png`, `f1_vs_speed.png`

3가지 모델을 동일 조건에서 비교했습니다.

| 모델 | 아키텍처 | Adversarial F1 | 추론 속도 |
|------|---------|:------:|:--------:|
| **KoELECTRA** | ELECTRA (RTD) | **86.04%** | **7.9ms** |
| BERT | BERT (MLM) | 85.17% | 10.4ms |
| DistilKoBERT | DistilBERT | 79.26% | 2.8ms |

핵심은 **실전 데이터에서의 차이**입니다. Val 데이터에서는 셋 다 95% 이상으로 비슷한데, 의도적으로 어렵게 만든 **적대적 테스트 450문장**으로 평가하면 진짜 실력이 드러납니다.

"같은 크기인데 왜 KoELECTRA가 더 좋은가?" — **사전학습 방식이 다릅니다.** BERT는 빈칸 채우기(MLM), ELECTRA는 토큰 교체 감지(RTD)로 학습합니다. 짧은 한국어 문장에서 미세한 의미 차이를 잡아내는 데 RTD가 유리했습니다.

**KoELECTRA — 정확도 최고, BERT보다 24% 빠름.** 최종 모델로 선택했습니다.

## 슬라이드 7: 개선 과정 — 3가지 교훈 (1.5분)

> 차트: `stage6_comparison.png`

KoELECTRA를 7단계에 걸쳐 개선했는데, **3가지 교훈**으로 요약하겠습니다.

**교훈 1: 데이터 품질 > 하이퍼파라미터.**
32가지 HP 조합을 탐색했는데 고작 +0.72%p. 반면 오분류를 분석해서 **약한 intent 타겟으로 98개만 보강**했더니 **+1.8%p**. 양보다 정확한 곳에 넣는 게 중요했습니다.

**교훈 2: "확신 있게 틀리는 것"이 가장 위험하다.**
오분류 63건 중 42건이 confidence 90% 이상인데 틀리는 과신뢰였습니다. Label Smoothing을 적용해서 **과신뢰 오류를 69% 줄였고**, confidence 0.85를 기준으로 "모르겠으면 되묻는" clarify 라우팅을 만들었습니다. 이게 실서비스에서 가장 중요한 안전장치입니다.

**교훈 3: 모델 탓만 하지 말고 라벨을 의심하라.**
가장 약한 doc_qa(76.6%)의 오분류 27건을 수동 검토했더니, **63%가 라벨 자체가 애매하거나 잘못된 경우**였습니다. 보정하면 실질 F1은 약 85%이고, doc 4개 intent는 모두 같은 Agent로 가니까 실서비스 영향도 제한적입니다.

최종: **Adversarial F1 87.58%, 추론 7.9ms, 과신뢰 -69%.**

## 슬라이드 8: 실전 검증 — 시나리오 테스트 (1분)

> 차트: `scenario_test_accuracy.png`

숫자만으로는 실서비스에서 되는지 모르니까, **100문장으로 실제 라우팅 시뮬레이션**을 했습니다. 학습에 안 쓴 제3의 LLM(Gemini)으로 생성하고 직접 검수했습니다.

| 유형 | 정확도 | 한 줄 요약 |
|------|:------:|----------|
| 표준 업무 입력 | **100%** | 정상적인 업무 요청은 완벽 |
| 초단문 (1~2어절) | **93%** | "기안서 양식" 같은 짧은 입력도 양호 |
| 경계 입력 | 79% | 두 intent 사이 애매한 문장 |
| 비속어/슬랭 | 76% | "쌉가능?" 같은 극단적 표현 |

핵심 메시지는 하나입니다. **일반적인 업무 입력은 완벽하게 처리합니다.** 어려운 경계 입력과 슬랭에서 틀리더라도, 앞서 만든 clarify 라우팅이 "혹시 이런 뜻이세요?"라고 되묻기 때문에 사용자가 체감하는 오류는 훨씬 적습니다.

## 예상 질문 & 답변 (백업)

**Q1: 왜 BERT가 아니라 KoELECTRA인가요?**

> 동일 크기(111M)에서 KoELECTRA가 Adversarial F1 0.87%p 높고 추론 24% 빠릅니다. 통계적 유의차(McNemar)는 없지만, 속도+강건성에서 우위라서 선택했습니다.

**Q2: Adversarial 87%면 실서비스에서 13%가 틀리나요?**

> Adversarial은 의도적으로 어렵게 만든 데이터입니다. 일반 입력(Val)에서는 98.9%입니다. 100문장 시나리오 테스트에서도 표준 입력은 100%입니다. 그리고 틀리더라도 confidence 0.85 이하면 사용자에게 되묻는 clarify 전략이 있어서 안전하게 처리됩니다.

**Q3: 데이터 2,900개면 적지 않나요?**

> 8개 분류에 카테고리당 ~360개이고, Val F1 98.9%에 도달했습니다. 실험에서 "양보다 품질이 중요하다"는 걸 확인했습니다. 하이퍼파라미터 32가지 조합보다 타겟 보강 98개가 +1.8%p로 훨씬 효과적이었습니다.

**Q4: Label Smoothing으로 F1이 떨어지는데 왜 적용했나요?**

> F1 하락이 -0.26%p로 미미한 반면, 과신뢰 오류가 42건에서 13건으로 69% 줄었습니다. 실서비스에서는 "확신 있게 틀리는 것"이 "살짝 못 맞추는 것"보다 훨씬 위험합니다. threshold 0.85로 정답/오답을 분리할 수 있게 된 것이 핵심 성과입니다.

**Q5: doc_qa가 76.6%로 낮은데 괜찮나요?**

> 수동 라벨 리뷰를 했더니 오류 27건 중 63%가 모델 문제가 아니라 라벨이 애매하거나 잘못된 경우였습니다. 보정하면 실질 F1은 약 85%입니다. 또한 doc_qa, doc_search, doc_generate, doc_summary 4개가 모두 같은 Document Agent로 라우팅되기 때문에 실서비스에서 사용자가 체감하는 오류는 훨씬 적습니다.

**Q6: LLM API에서 sLLM으로 교체하면 성능이 떨어지지 않나요?**

> Intent 분류기는 이미 sLLM(KoELECTRA)으로 동작 중이고 성능이 검증됐습니다. 판단/문서 Agent도 LLM API로 input/output 형태를 확정한 상태에서 파인튜닝하기 때문에, 동일 품질을 목표로 학습합니다. 교체 후 성능 비교 실험도 진행할 예정입니다.
