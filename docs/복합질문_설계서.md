## 1. 문제 정의

현재 Intent 분류 시스템은 **단일 intent만 반환**한다. "규정 찾아서 판단해줘" 같은 복합 질문에서 하나의 intent만 분류되어 나머지 의도가 무시됨.

### 현재 성능 (실험 7 기준)
| 모델 | F1 (212문장) | 속도 | 비용 |
|------|:-----------:|:----:|:----:|
| **BERT sLLM** | 90.07% | 7.48ms | $0 |
| GPT-4o-mini | 86.30% | 583.7ms | ~$0.09 |

## 2. 아키텍처: 2-Layer Smart Hybrid

### 핵심 결정: sLLM vs LLM 역할 분담

| 역할 | 담당 | 근거 | 4단계 이후 |
|------|------|------|----------|
| **Intent 분류 (단순)** | sLLM (BERT) | F1 90%+, GPT보다 나음, 7ms, $0 | 유지 |
| **복합 감지** | sLLM + 규칙 | top-k 확률 + 키워드 + 동사 카운트 | 유지 |
| **분류+분해 (복합)** | LLM API | 분류+분해+순서를 한번에 처리 | sLLM 교체 예정 |
| **맥락 해석** | LLM API | chat_history 참조 필요 | sLLM 교체 예정 |

### 그래프 구조 (v2)

```
[사용자 입력]
      │
[classify_intent_v2]  ← BERT + 복합감지 + 지시어감지 (sLLM, 7ms)
      │
 ┌────┴────────┬───────────┬──────────────┐
 단순(80%)    복합(20%)   맥락의존      낮은confidence
 │            │            │              │
 기존Agent    decompose    resolve_ctx    clarify_candidates
 직행         +classify    →재분류         (top-3 제시)
              │
         execute_sub_queries (순차 실행)
              │
         merge_responses (섹션별 통합)
              │
         [format_response → END]
```

### 예상 성능

| 시나리오 | 단순 쿼리 (80%) | 복합 쿼리 (20%) | 가중 평균 |
|---------|:--------------:|:--------------:|:--------:|
| **속도** | 7ms (BERT) | ~500ms (LLM) | ~106ms |
| **비용** | $0 | ~$0.01 | ~$0.002 |

## 4. 핵심 설계 결정

### 4.1 복합 감지: 3중 AND 로직

키워드 **단독으로는** 복합 판정 안 함. 3개 조건 중 **2개 이상** 충족 시에만 복합.

1. **접속/순차 키워드** — "~해서", "~하고", "~후에", "~아서/어서", "~고", "~면서", "~한 뒤에" 등
2. **top-2 confidence gap < 0.3** — 두 intent가 경합 중
3. **동사 어미 2개 이상** — 행위가 2개 이상

### 4.2 LLM 분해 시 한번에 분류+분해

- (기존안) 복합감지 → LLM분해 → BERT 재분류 → Agent
- (채택안) 복합감지 → **LLM이 분류+분해를 한번에** → Agent 직행
- 이유: LLM이 분해할 때 이미 각 서브쿼리 의도를 이해하므로 BERT 재분류는 불필요한 오버헤드

### 4.3 안전한 실패

- LLM 분해 실패/검증 실패 → BERT 단일 분류로 **자동 fallback**
- 최악의 경우 = 현재 시스템과 동일하게 동작

### 4.4 설계 제약

| 항목 | 결정 |
|------|------|
| 서브쿼리 최대 개수 | 3개 (초과 시 "나눠서 질문해주세요") |
| Conditional 로직 | 미지원 (sequential/parallel만) |
| 재시도 횟수 | 최대 1회 |
| Chat history 범위 | 최근 5턴 |
| 부분 실패 처리 | 성공 결과만 표시, 실패는 "처리 실패" 메시지 |

## 6. SSE 이벤트 흐름

### 단순 쿼리 (기존과 동일)
```
intent → status → [token...] → result → done
```

### 복합 쿼리
```
intent(is_complex=true) → status("복합 질문 감지")
→ multi_intent(sub_queries)
→ sub_query_done(step=1) → sub_query_done(step=2)
→ status("결과 통합 완료")
→ token(message) → result(multi_intent) → done
```

### 맥락 의존 쿼리
```
intent → status("맥락 해석 중")
→ status("맥락 해석 완료 → 재분류 중")
→ intent_update (재분류 결과)
→ status → [token...] → result → done
```

## 7. 토크나이저 버그 발견 및 수정

회귀 테스트 중 기존에 잠재해 있던 **토크나이저 불일치 버그**를 발견·수정함.

### 문제
- `ai/models/intent_classifier/tokenizer_config.json`의 `tokenizer_class`가 `"TokenizersBackend"`(무효값)로 저장되어 있었음
- `"BertTokenizerFast"`로 수정하여 로드는 성공했지만, 로컬 모델 디렉토리의 vocab 파일이 `klue/bert-base` 원본과 불일치
- 결과: 동일 모델인데 **로컬 토크나이저 사용 시 F1 80.54%**, klue/bert-base 토크나이저 사용 시 **F1 90.07%** (10%p 차이)

### 원인
RunPod에서 모델 저장 시 토크나이저 파일이 비정상적으로 기록됨. 기존 실험 스크립트들은 `klue/bert-base`에서 직접 토크나이저를 로드하여 문제가 드러나지 않았지만, 실서비스(`intent_classifier.py`)는 로컬 모델 디렉토리에서 로드하고 있었음.

### 수정
`intent_classifier.py`에서 토크나이저를 `klue/bert-base` 원본에서 로드하도록 변경:
```python
# 변경 전
self.tokenizer = AutoTokenizer.from_pretrained(str(model_dir))
# 변경 후
self.tokenizer = AutoTokenizer.from_pretrained("klue/bert-base")
```

### 검증
| 토크나이저 | adversarial F1 | blind F1 |
|-----------|:--------------:|:--------:|
| 로컬 (버그) | 80.54% | 94.25% |
| **klue/bert-base (수정 후)** | **90.07%** | **95.62%** |
| 기존 실험 7 결과 | 90.07% | 92.84% |

→ 수정 후 기존 실험 결과와 **정확히 일치**. 실서비스에서도 실험과 동일한 성능 보장.

## 8. 검증 결과 (Phase 3, 2026-02-16 완료)

### 테스트 데이터
- **30문장** 신규 제작 (`data/training/intent/complex_test.json`)
- 구성: 단순(오탐 테스트) 10 + 복합 10 + 맥락 의존 5 + 경계 5

### 결과

| 기능 | 정확도 | 세부 |
|------|:------:|------|
| **복합 감지** (`detect_complexity`) | **25/30 (83.3%)** | 오탐 5건, 미감지 0건 |
| **맥락 감지** (`is_context_dependent`) | **30/30 (100.0%)** | 완벽 |

### 카테고리별 결과

| 카테고리 | 복합 감지 | 맥락 감지 |
|---------|:--------:|:--------:|
| simple_false_positive (10) | 6/10 | 10/10 |
| complex_true (10) | **10/10** | 10/10 |
| context_dependent (5) | 4/5 | **5/5** |
| boundary (5) | **5/5** | 5/5 |

### 오탐 분석 (5건)

5건 모두 `keyword_pattern + confidence_gap` 동시 트리거:
- "규정 확인해서 알려줘" — '확인해서'가 접속 패턴이지만 단순 doc_search
- "내일 일정 확인하고 알려줘" — '확인하고'가 접속이지만 단순 schedule_view
- "출장 관련 규정을 검토해서 정리해줘" — '검토해서'가 접속이지만 단순 doc_search
- "팀 보고서 양식에 맞게 작성해줘" — 키워드 패턴에 걸림
- "그거 보고서로 정리해줘" — '정리해줘'가 접속 패턴에 걸림

**원인**: 테스트에서 더미 candidates(gap=0.25)를 사용하여 confidence_gap 조건이 항상 트리거됨. 실제 BERT는 단일 의도 문장에서 top-1 confidence가 높아(>0.9) gap이 넓어지므로(>0.3) 오탐이 감소함.

**결론**: 3중 AND 로직의 핵심은 **confidence gap이 BERT의 실제 확률과 결합될 때** 오탐 방지 역할을 함. 키워드 패턴만으로는 오탐 가능성이 있으나, BERT confidence와 결합하면 실효성 있음.
