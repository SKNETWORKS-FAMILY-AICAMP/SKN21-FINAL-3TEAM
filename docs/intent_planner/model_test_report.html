평가 지표 설명

Held-out 정확도
학습에 전혀 사용하지 않은 별도 테스트셋(100건)으로 측정한 정확도. Dev(개발) 점수와 달리 실제 일반화 성능을 반영.
과적합 gap (Dev - Held-out)
Dev 점수와 Held-out 점수의 차이. gap이 클수록 모델이 학습 데이터에만 맞춰져 새로운 입력에 약함. ±5%p 이내가 이상적.
앙상블 (Ensemble)
동일 모델을 서로 다른 seed(초기값)로 5번 학습 → 5개 모델이 투표해서 최종 답을 결정. 개별 모델의 실수를 서로 보정.
GPT Knowledge Distillation (KD)
GPT-4가 생성한 고품질 학습 데이터로 작은 모델을 학습시키는 기법. 큰 모델의 지식을 작은 모델에 전달.

평가 지표 설명

Perfect Match (PM)
모델이 출력한 plan이 정답과 완전히 일치하는 비율. intent 종류, 순서, 의존성(depends_on)이 모두 맞아야 정답.
Weighted Score
5가지 세부 지표의 가중 합산 (0~1). Intent Recall(30%) + Order(25%) + Precision(20%) + Dep Correctness(15%) + Efficiency(10%).
Step Collapse Rate
3-step을 2-step으로 축소하는 등 단계를 줄여버리는 오류 비율. 낮을수록 좋음.

Few-shot에 포함된 3-step 예시
예시 1 — 직렬 의존성
"출장 규정 문서 찾아서 해외출장 가능한지 확인하고 출장 보고서 만들어줘"
→ doc_retrieve → judgment → doc_generate (1→2→3)
예시 2 — 병렬 → 합류
"연차 규정 확인하고 팀 일정 보고 비는 날에 휴가 등록해줘"
→ judgment + schedule_view(병렬) → schedule_add (1,2→3)
예시 3 — 병렬 검색 → 생성
"마케팅 보고서 찾고 경쟁사 자료도 검색해서 비교 제안서 만들어줘"
→ doc_retrieve + doc_retrieve(병렬) → doc_generate (1,2→3)
왜 효과가 있나? — 모델이 예시를 보고 "이렇게 쪼개는 거구나"를 이해합니다. 학습 데이터를 추가하지 않고 프롬프트만으로 성능을 올리는 기법이에요. 4-step 테스트에서 기본(3.3%) → 하이브리드(16.7%)로 +13.4%p 개선된 이유가 이것입니다.

4-step / 5-step 일반화 테스트

"3-step까지만 학습한 모델이 4-step, 5-step도 잘 분류하는지 확인"
실험 배경
최종 Planner 모델(v5)은 최대 3-step까지의 데이터(1,471건)로 학습되었습니다. 학습에 없던 4-step(30건)과 5-step(30건) 테스트셋을 별도 제작하여 일반화 능력을 검증했습니다.
테스트 설계
4-step 테스트 (30건) (클릭)
시스템 프롬프트: "최대 4단계" (기본값)
토폴로지: 직렬, 병렬 시작, 다이아몬드형
예: "출장 규정 찾아서 해외출장 확인하고, 보고서 만들어서 일정 등록해줘"
5-step 테스트 (30건) (클릭)
시스템 프롬프트: "최대 5단계" (--max-steps 5)
토폴로지: 직렬 5단, 병렬+합류, 다이아몬드+분기 등
예: "보고서랑 분석자료 찾아서 비교 분석하고, 제안서 만들어서 발표 일정 잡아줘"
4-step 토폴로지 패턴
직렬 — 앞이 끝나야 다음 시작
1 → 2 → 3 → 4
"규정 찾아서 → 가능한지 확인하고 → 보고서 만들어서 → 일정 등록해줘"
병렬 시작 — 두 작업을 동시에 하고 합류
1, 2 (동시) → 3 → 4
"보고서랑 분석자료 둘 다 찾아서 → 비교 판단하고 → 제안서 만들어줘"
다이아몬드 — 갈라졌다 합류
1 → 2, 3 (동시) → 4
"규정 확인하고 → 일정도 보고 + 문서도 찾아서 → 종합 문서 만들어줘"
5-step 토폴로지 패턴
직렬 5단 — 순차적으로 5단계
1 → 2 → 3 → 4 → 5
"규정 찾아서 → 확인하고 → 일정 봐서 → 보고서 만들고 → 일정 등록해줘"
병렬+합류 — 처음에 동시 진행 후 합류
1, 2 (동시) → 3 → 4 → 5
"보고서랑 분석자료 찾아서 → 비교 분석하고 → 제안서 만들어서 → 일정 잡아줘"
다이아몬드+분기 — 갈라지고 합류 후 다시 분기
1, 2, 3 (동시) → 4 → 5
"규정 확인하고 + 일정 확인하고 + 문서도 찾아서 → 종합 문서 만들고 → 연차 등록해줘"
결과 요약
테스트 PMPerfect Match
모델 출력이 정답과 완전히 일치하는 비율. intent 종류, 순서, 의존성이 모두 맞아야 정답. 가장 엄격한 지표.		 WSWeighted Score
5가지 세부 지표의 가중 합산 (0~100%). IR(30%) + Order(25%) + IP(20%) + Dep(15%) + Efficiency(10%). PM보다 관대한 부분 점수.		 IRIntent Recall
정답에 있는 intent를 모델이 얼마나 빠뜨리지 않고 찾았는가. 예: 정답이 3개인데 2개만 출력하면 66.7%.		 IPIntent Precision
모델이 출력한 intent 중 실제로 맞는 비율. 100%면 잘못된 intent를 하나도 만들어내지 않았다는 뜻 (환각 없음).		 Dep의존성 정확도 (Dep Correctness)
각 step의 depends_on(선행 조건)이 정답과 얼마나 일치하는지. 예: step 3이 [1,2]에 의존해야 하는데 [1]만 적으면 감점.		 SCRStep Collapse Rate
정답보다 step 수를 줄여버리는 오류 비율. 예: 4step이 정답인데 3step으로 축소. 낮을수록 좋음.

Intent Precision 100% — "모델이 출력한 것 중 틀린 게 없다"
Precision은 모델이 출력한 것 → 정답 방향으로 검증합니다. "모델이 엉뚱한 걸 추가하지 않았는가?"를 측정합니다.
입력: "출장 규정 찾아서 해외출장 확인하고, 보고서 만들어서 일정 등록해줘"
정답: doc_retrieve → judgment → doc_generate → schedule_add (4개)
모델: doc_retrieve → judgment → schedule_add (3개)
모델이 출력한 3개 중 3개가 정답에 있음 → Precision = 3/3 = 100%
빠뜨린 건 있지만(doc_generate 누락), 엉뚱한 intent를 추가하지는 않았다는 뜻입니다.
Intent Recall 86~92% — "정답 중 대부분을 찾았지만 일부 누락"
Recall은 정답 → 모델이 출력한 것 방향으로 검증합니다. "정답에 있는 걸 빠뜨리지 않았는가?"를 측정합니다.
같은 예시:
정답: doc_retrieve → judgment → doc_generate → schedule_add (4개)
모델: doc_retrieve → judgment → schedule_add (3개 — doc_generate 누락)
정답 4개 중 3개를 모델이 찾음 → Recall = 3/4 = 75%
step을 합쳐버려서 일부를 빠뜨리는 것이지, intent 종류를 틀리는 게 아닙니다.
Precision vs Recall 요약
Precision = 모델 출력 중 맞는 비율
엉뚱한 걸 추가했는가? → 안 함 (100%)
Recall = 정답 중 찾은 비율
있어야 할 걸 누락했는가? → 일부 누락 (86~92%)
Intent 환각 0건 — "없는 intent를 만들어내지 않았다"
사용 가능한 intent: doc_retrieve, judgment, doc_generate, schedule_add, schedule_view, general
모델이 이 6개 외의 intent(예: "doc_compare", "schedule_delete" 등)를 지어낸 적이 단 한 건도 없음
4-step, 5-step처럼 학습에 없던 복잡한 요청에서도 존재하는 intent만 정확하게 사용했습니다.
모델이 혼란스러울 때 엉뚱한 라벨을 만들어내는 "환각" 현상이 전혀 없다는 뜻입니다.
Weighted Score 86~89% — "완전히 틀린 게 아니라 거의 맞춘다"
PM(Perfect Match)은 하나라도 틀리면 0점인 엄격한 지표입니다.
WS(Weighted Score)는 부분 점수를 줍니다:
Intent Recall(30%) + 순서(25%) + Precision(20%) + 의존성(15%) + 효율성(10%)
PM이 3~17%로 낮아 보이지만, WS가 86~89%라는 것은 대부분의 intent와 순서를 맞추고 있다는 뜻입니다.
step 개수나 의존성에서 살짝 어긋나서 PM에서 탈락하는 거지, 완전히 엉뚱한 답을 내는 건 아닙니다.
결론
1. 3-step 학습 모델은 4-5step으로 구조적 일반화가 안 됨 — PM 3~17%
2. 하지만 intent 분류 자체는 정확 — IP 100%, 환각 0건, 오답 원인은 step 개수와 의존성
3. 하이브리드 프롬프트가 4-step에서 3.3% → 16.7%로 개선 효과 있음
4. 실서비스에서 4-5step 요청은 극히 드묾
