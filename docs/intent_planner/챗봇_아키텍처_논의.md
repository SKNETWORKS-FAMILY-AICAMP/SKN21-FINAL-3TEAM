## 1. 전체 챗봇 흐름

```
사용자 입력
  │
  ▼
[전처리] ← P1~P4: 맞춤법/줄임말/특수문자 정리
  │
  ▼
[BERT 분류] ← klue/bert-base (7ms, 로컬, $0)
  │         7개 intent: judgment, doc_search, doc_generate,
  │         meeting_generate, schedule_add, schedule_view, general
  │
  ├── 단일 질문 (confidence ≥ 0.7)
  │     └→ sLLM Agent 실행 (judgment / document / schedule)
  │
  ├── 복합 질문 (2개+ 신호 감지)
  │     └→ GPT API 1회 호출 (분해) → sLLM Agent 순차 실행
  │
  ├── General intent
  │     └→ sLLM 단독 (시스템 프롬프트로 업무 범위 제한)
  │
  ├── 낮은 confidence (< 0.7)
  │     └→ top-3 후보 제시 → 사용자 선택
  │
  └── 지시어 감지 ("그거", "아까 그" 등)
        └→ LLM 맥락 해석 → 재분류
```

## 2. 확정된 결정사항

### 2-1. 단일 질문 처리 (대다수 요청)

```
BERT 분류 (7ms, $0) → sLLM Agent 실행
```

- BERT가 7개 intent 중 하나로 분류
- confidence ≥ 0.7이면 해당 Agent로 바로 라우팅
- sLLM이 실제 업무 처리 (RAG 검색, 문서 생성, 일정 관리 등)

### 2-2. 복합 질문 처리 — 하이브리드 B방식

```
BERT 감지 → GPT 1회 분해 → sLLM Agent 순차 실행
```

- **감지 로직** (`detect_complexity`): 3중 조건 AND, 2개 이상 충족 시 복합 판정
  1. 접속/순차 키워드 패턴 ("~해서", "~하고", "~한 뒤에" 등)
  2. top-2 confidence gap < 0.3 (두 intent가 경합 중)
  3. 동사 어미 2개 이상 ("찾아줘", "만들어줘" 등)
- **분해**: GPT API 1회 호출로 서브쿼리 분리 + intent 배정 + 실행순서 결정
- **실행**: sLLM Agent가 각 서브쿼리를 순차 실행 (의존성 있으면 이전 결과 전달)
- **병합**: `merge_responses`에서 섹션별로 결과 통합
- **제한**: 서브쿼리 최대 3개 (`MAX_SUB_QUERIES=3`), 초과 시 사용자에게 나눠서 질문 요청

**왜 하이브리드인가?**
- GPT는 분해(1회)에만 사용 → 비용 최소화
- 실제 업무 처리는 전부 sLLM → 발표 때 "sLLM 파이프라인" 스토리 유지
- 현재는 `ENABLE_COMPLEX_QUERY=False`로 비활성화 상태 (단일 intent로만 운영)

### 2-3. General Intent 처리 — sLLM Only

```
General → sLLM (시스템 프롬프트: 업무 범위 제한)
```

- 템플릿 기반 하이브리드는 **불필요** → sLLM 단독으로 충분
- 시스템 프롬프트로 업무 범위 제한:
  > "당신은 업무 도우미 '듀듀'입니다. 규정 판단, 문서 검색/생성, 회의록, 일정 관리만 지원합니다."
- 8B 모델이면 인사/감사/도움 요청 정도는 충분히 처리
- 하드코딩 fallback은 sLLM 서버 에러 시에만 적용

### 2-4. 핵심 원칙

> **"LLM 챗봇이 아닌 사내 업무 도우미"**

- 범용 대화 능력이 아닌, 특정 업무 처리에 집중
- GPT 사용 최소화 (복합질문 분해 1회만)
- sLLM 중심 파이프라인 → 비용 최적화 + 보안 (사내 데이터 외부 유출 방지)
- 발표 스토리: "단일 질문은 BERT($0, 7ms), 복합 질문은 LLM 1회 분해, 나머지는 전부 로컬 sLLM"

## 3. 현재 시스템 현황

### 3-1. 파일 구조

| 파일 | 역할 |
|------|------|
| `ai/agents/intent_classifier.py` | BERT 분류기 + 복합감지 + 오분류 보정 |
| `ai/agents/orchestrator.py` | LangGraph 그래프 (v2 Smart Hybrid) |
| `ai/agents/config.py` | 임계값 상수 모음 |
| `ai/agents/state.py` | AgentState 타입 정의 |
| `ai/agents/preprocessing.py` | 전처리 (P1~P4) |
| `ai/models/intent_classifier/` | BERT weights 저장 위치 |

### 3-2. 설정값 (config.py)

| 상수 | 값 | 설명 |
|------|------|------|
| `INTENT_CONFIDENCE_THRESHOLD` | 0.7 | 이하면 clarify (top-3 후보 제시) |
| `INTENT_FALLBACK_THRESHOLD` | 0.5 | 이하면 general 강제 |
| `ENABLE_COMPLEX_QUERY` | False | 복합질문 분해 활성화 여부 (현재 비활성) |
| `COMPLEXITY_GAP_THRESHOLD` | 0.3 | top-2 confidence gap 임계값 |
| `MAX_SUB_QUERIES` | 3 | 복합질문 최대 서브쿼리 수 |
| `CONTEXT_HISTORY_TURNS` | 5 | 맥락 해석 시 참조할 대화 턴 수 |

### 3-3. Fallback 체인 (모델 없을 때)

```
BERT weights 있음? → BERT 추론
  ↓ 없음
Solar API 키 있음? → Solar LLM 기반 분류
  ↓ 없음
Embedding 모델? → ko-sbert-nli 유사도 기반 분류
```

### 3-4. 알려진 오분류 보정 (KNOWN_OVERRIDES)

BERT가 잘못 분류하는 패턴을 정규식으로 강제 보정:
- "인센티브 지급 기준" → doc_search 대신 **judgment**
- "남은 공휴일" → general 대신 **schedule_view**
- "규정 알려줘" → doc_search 대신 **judgment**
- "복리후생 뭐 있어" → **judgment**
- "지각하면 어떻게 돼?" → general 대신 **judgment**

## 4. 남은 논의 사항

### 4-1. 복합질문 감지 로직 개선 (`detect_complexity`)
- [ ] 현재 3중 조건이 적절한지 실데이터로 검증 필요
- [ ] False positive 케이스 수집 (단순 질문인데 복합으로 오판하는 경우)
- [ ] False negative 케이스 수집 (복합인데 놓치는 경우)
- [ ] `COMPLEXITY_GAP_THRESHOLD` 값 튜닝 (현재 0.3)

### 4-2. GPT 분해 프롬프트 설계
- [ ] `decompose_and_classify` 프롬프트 품질 검증
- [ ] BERT 힌트를 주는 것이 분해 품질에 도움이 되는지 A/B 테스트
- [ ] 분해 결과의 intent 정확도 측정
- [ ] `_validate_decomposition` 검증 로직 충분한지 확인

### 4-3. 서브쿼리 실행/합치기 방식
- [ ] `depends_on` 체인이 길어질 때의 성능 (3단계 순차 실행 시 지연)
- [ ] 병렬 실행 (`execution_type: "parallel"`) 구현 여부 결정
- [ ] `merge_responses` 텍스트 포맷 개선 (현재는 단순 나열)
- [ ] 서브쿼리 간 context 전달 방식 최적화

### 4-4. sLLM 모델 선택 및 파인튜닝 범위
- [ ] 8B급 모델 선정 (Llama 3, Gemma, Qwen 등)
- [ ] 파인튜닝 데이터셋 구성 범위 결정
  - judgment: 규정 기반 Q&A
  - doc_generate: 문서 템플릿 기반 생성
  - meeting_generate: 회의록 요약
  - schedule: 날짜/시간 파싱
- [ ] LoRA vs Full fine-tuning 결정
- [ ] vLLM 서빙 환경 구성 (RunPod A100)

### 4-5. `ENABLE_COMPLEX_QUERY` 활성화 시점
- [ ] 단일 intent 파이프라인이 안정화된 후 활성화
- [ ] 팀원 Agent (judgment, document, schedule) 완성이 선행 조건
- [ ] 활성화 전 테스트 시나리오 준비

### 4-6. Post-execution 재분류 (`post_execution_check`)
- [ ] Agent 완성 후 "빈약한 결과" 판정 기준 정의
- [ ] 재분류 시 무한루프 방지 (최대 1회 재시도)
- [ ] judgment Agent: RAG 결과 0건이면 재분류
- [ ] doc_search Agent: 검색 결과 없으면 재분류

## 5. 그래프 구조 (LangGraph v2)

```
[사용자 입력]
      │
[classify_intent_v2]  ← BERT 분류 + 복합 감지 + 지시어 감지
      │ (route_by_complexity)
      ├── simple          → 기존 단일 Agent (BERT 결과 그대로)
      ├── complex         → decompose_and_classify → execute_sub_queries → merge_responses
      ├── context_dep     → resolve_context → classify_intent_v2 (재분류)
      ├── low_confidence  → clarify_with_candidates (top-3 후보 제시)
      │
[format_response] → END
```
