# Intent 분류 실험 — 발표 대본

> 예상 소요: 10~15분 | 멘토 리뷰용 | 2026-02-20

---

## 도입 (1분)

안녕하세요. Intent 분류 실험에 대해 말씀드리겠습니다.

저희 서비스는 사용자 입력을 7개 업무 의도로 분류해서 적절한 Agent로 라우팅하는 구조입니다. 예를 들어 "이거 규정 위반이야?"는 judgment Agent로, "보고서 작성해줘"는 document Agent로 보내는 식입니다.

여기서 핵심 의사결정이 하나 있었습니다. **이 분류를 GPT 같은 LLM API로 할 것인가, 아니면 BERT를 파인튜닝한 sLLM으로 할 것인가**. 이걸 9단계 실험으로 검증했습니다.

---

## 실험 1: 왜 sLLM을 선택했나 (1분)

먼저 6가지 방법론을 비교했습니다. Rule-based부터 GPT Few-shot까지요.

결과만 보면 GPT Few-shot이 F1 97.5%로 가장 높고, BERT 파인튜닝은 90%입니다. 7.5%p 차이가 납니다.

그런데 속도를 보면 BERT가 6.7ms, GPT가 456ms입니다. **68배 차이**입니다. 그리고 비용은 BERT가 $0이고 GPT는 건당 과금됩니다.

저희 서비스는 매 대화마다 intent 분류를 거치기 때문에, 속도와 비용이 중요합니다. 그래서 **정확도를 올려서 격차를 줄이는 방향으로 sLLM을 선택**했습니다.

---

## 실험 2~3: 문제 발견과 해결 (1.5분)

혼동행렬을 분석해보니 judgment와 general 경계에서 가장 많이 틀렸습니다. "이거 규정에 어긋나는 거 아냐?" 같은 캐주얼한 표현을 general로 분류하는 거죠.

원인을 찾아보니 judgment 학습 데이터의 92%가 격식체였습니다. "규정 위반 여부를 판단해주십시오" 같은 문장만 학습해서 캐주얼한 표현을 모르는 겁니다.

그래서 judgment에 캐주얼 데이터 50건을 추가했더니 Adversarial 정확도가 **72%에서 88%로, 16%p 올랐습니다**. 오분류 5건이 0건이 됐고요.

여기서 얻은 교훈이 있습니다. **모델이 틀리는 건 모델 자체의 한계가 아니라 데이터의 편향인 경우가 많다**는 겁니다.

---

## 실험 4: 체계적 데이터 증강 (1.5분)

이 교훈을 바탕으로 체계적으로 데이터를 증강했습니다.

v1.2에서는 인터넷 슬랭, 초성, 축약어 같은 **비정형 데이터 300건**을 추가했습니다. "ㅎㅇㄹ 정리해줘", "걍 일정 알려줘" 같은 실사용자 패턴입니다.

v1.3에서는 v1.2에서 틀린 18건을 분석해서 **혼동 패턴별로 타겟 증강 163건**을 했습니다. judgment-general 경계, 초단문, 복합 의도 등 약점 패턴에 집중했죠.

결과적으로 Adversarial이 **85%에서 91.67%까지 올랐습니다**.

재미있는 건 v1.4입니다. 같은 데이터로 하이퍼파라미터 그리드서치를 6가지 돌렸는데, **오히려 성능이 떨어졌습니다**. 과적합이 발생한 거죠. 여기서 **데이터 품질이 하이퍼파라미터보다 중요하다**는 결론을 얻었습니다.

---

## 실험 5: 모델 전탐색 (1분)

다른 모델도 시도했습니다. klue/bert-base, klue/roberta-base, koelectra-base-v3 이렇게 3개 모델에 대해 각각 51번씩, **총 153번 학습**했습니다.

하이퍼파라미터 조합은 epochs 4종, learning rate 4종, batch size 3종, warmup 3종입니다. 2단계로 나눠서 Step 1에서 144번 돌려 좁히고, Step 2에서 9번 미세 조정했습니다.

결과적으로 3개 모델 성능이 거의 동급이었습니다. Eval F1은 98.2% 부근으로 거의 같고, **Adversarial에서 BERT가 90.15%로 가장 높아서** 최종 선택했습니다.

---

## 실험 6: 전처리 Ablation (1.5분)

전처리 파이프라인도 실험으로 검증했습니다. 4단계 전처리를 하나씩 쌓아가면서 기여도를 측정했습니다. Ablation Study라고 하는 방법입니다.

공백 정리만 적용했을 때, 맞춤법 교정 추가했을 때, 초성 복원까지 넣었을 때, 슬랭 정규화까지 전체 적용했을 때 — 이렇게 5가지 조합을 비교했습니다.

결과적으로 전처리 전체 적용 시 **+1.3%p 개선**이 있었고, 모든 seed에서 일관되게 개선됐습니다.

여기서 중요한 부수적 발견이 있었습니다. **seed에 따라 성능이 최대 4.5%p까지 차이**가 납니다. seed 42에서 90.8%인데 seed 456에서 86.3%입니다. 그래서 이후 실험부터는 **seed 3개 평균과 표준편차**로 보고하기 시작했습니다.

---

## 실험 7: BERT vs GPT 최종 대결 (1.5분)

이게 가장 중요한 실험입니다. 실험 1에서는 70문장으로 비교했었는데, 이번에는 **212문장으로 동일 조건에서 비교**했습니다.

결과가 뒤집혔습니다. BERT+전처리가 F1 90.07%, GPT Few-shot이 86.30%입니다. **BERT가 3.8%p 앞섰습니다**.

왜 뒤집혔을까요? 70문장에서 212문장으로 늘리면서 1~2어절 짧은 입력이 많이 포함됐는데, GPT가 여기서 21건이나 틀렸습니다. "규정", "일정", "보고서" 같은 단어만 입력하면 GPT는 general로 분류하는 반면, BERT는 학습 데이터에서 이런 패턴을 배워서 맞추는 겁니다.

반대로 BERT가 틀리는 11건은 "아까 그거 다시 해줘" 같은 맥락 의존적 질문이었습니다. 이건 대화 히스토리가 필요한 거라 분류기 단독으로는 한계가 있는 영역이고, **오케스트레이터에서 처리하도록 설계**했습니다.

---

## 실험 8: 통계적 검증 — 정직하게 (1분)

여기서 한 가지 정직하게 말씀드릴 부분이 있습니다.

McNemar 검정 결과 p값이 0.1116입니다. 통계적으로 유의미한 차이가 아닙니다. 즉 **BERT가 GPT보다 정확도가 높다고 통계적으로 주장할 수는 없습니다**.

Bootstrap으로 신뢰구간을 구하면 BERT의 F1이 95% 확률로 85.5%에서 93.8% 사이입니다.

그래서 저희의 결론은 이렇습니다. **"정확도는 동급이다. 하지만 속도가 45배 빠르고 비용이 $0이다."** 이게 sLLM을 선택한 정당한 근거입니다.

---

## 실험 9: Blind 평가 (1분)

마지막으로 **모델 개발 과정에서 한 번도 사용하지 않은 독립 테스트셋** 70문장으로 최종 검증했습니다.

Adversarial 테스트셋은 실험 5~7에서 반복 사용했기 때문에 연구자가 결과를 보고 데이터나 모델을 조정했을 가능성이 있습니다. 간접적인 데이터 누출이죠. Blind 테스트셋은 이런 영향이 전혀 없습니다.

결과는 Blind F1 **92.84%**로, Adversarial(90.07%)보다 오히려 높았습니다. 모델이 과적합되지 않았다는 긍정적 신호입니다.

Confidence threshold도 분석했는데, 0.7을 기준으로 설정하면 precision 93%, coverage 95.7%로 균형이 좋았습니다. 다만 confidence가 0.9 이상인데 틀리는 케이스가 오분류의 57.7%라서, **confidence 점수만으로는 폴백 판단이 부족하고 오케스트레이터 레벨에서 맥락 기반 검증이 필요하다**는 결론입니다.

---

## 마무리 (30초)

정리하면:

1. **sLLM 선택 근거**: 정확도 동급 + 속도 45배 + 비용 $0
2. **개선 방법론**: 데이터 품질 중심의 체계적 증강 (72% → 91.67%)
3. **검증의 투명성**: seed 분산, McNemar 검정, 독립 Blind 평가까지 수행
4. **한계 인식**: overconfident error 57.7%, 초단문 불안정 → 오케스트레이터에서 보완

총 9개 실험, 153번 모델 학습, 282문장 테스트를 통해 검증했습니다.

질문 있으시면 말씀해 주세요.

## 예상 질문 & 답변

**Q1: 왜 GPT-4o가 아니라 GPT-4o-mini로 비교했나요?**

> 저희 서비스에서 intent 분류는 매 대화마다 호출되는 빈번한 작업입니다. GPT-4o는 비용이 4o-mini의 약 15배라 실서비스 적용이 비현실적이고, 4o-mini가 intent 분류 같은 단순 작업에서 4o와 성능 차이가 크지 않아 현실적인 비교 대상으로 선택했습니다.

**Q2: 1,916문장이면 데이터가 적은 것 아닌가요?**

> 7개 카테고리 분류에 카테고리당 약 270문장이고, BERT 파인튜닝에는 충분한 수준입니다. 실제로 Eval F1이 98.2%에 도달했고, v1.3→v1.4에서 데이터 양이 아닌 품질이 성능을 결정한다는 걸 확인했습니다. 무작정 양을 늘리기보다 **오분류 패턴을 분석해서 타겟 증강**하는 게 효과적이었습니다.

**Q3: Adversarial 90%면 실서비스에서 10%가 틀린다는 건가요?**

> Adversarial 테스트셋은 의도적으로 어렵게 만든 데이터입니다. 초성 입력, 1어절 입력, 맥락 의존 질문 등이 포함되어 있어서 실사용 분포보다 훨씬 까다롭습니다. 독립 Blind 테스트에서는 92.8%였고, 일반 입력(Eval)에서는 98.2%입니다. 그리고 틀리더라도 general로 폴백하는 안전한 실패를 하고, confidence가 낮으면 사용자에게 되묻는 clarify 전략을 적용합니다.

**Q4: 전처리 +1.3%p면 효과가 작은 것 아닌가요?**

> 수치만 보면 작아 보이지만 두 가지를 고려해야 합니다. 첫째, 이미 88% 수준에서의 +1.3%p는 오분류를 약 10% 줄이는 효과입니다. 둘째, seed 3개 전부에서 일관되게 개선된 걸 확인했기 때문에 노이즈가 아닌 실제 효과입니다. 또한 전처리는 추론 시 비용이 거의 0이라 넣지 않을 이유가 없습니다.

**Q5: 4단계에서 LoRA 파인튜닝하면 어떻게 되나요?**

> 현재 BERT(111M)에서 더 큰 모델(예: Solar 10.7B)에 LoRA를 적용하면 맥락 이해력이 올라가서 현재 BERT의 약점인 맥락 의존 질문과 복합 질문 처리가 개선될 것으로 기대합니다. 코드 구조는 LLM 호출 인터페이스만 교체하면 되도록 설계되어 있어서 모델 교체가 간단합니다.

## 부록: 데이터 예시

### 1) Base 학습 데이터 (v1.0 — 7카테고리 × 200문장)

형식: JSONL (한 줄 = 한 문장)

```jsonl
// judgment — 규정/규칙 기반 판단
{"text": "연차 사용 시 하루 전에 신청해도 되나요?", "label": "judgment"}
{"text": "야근 수당은 몇 시 이후부터 적용되나요?", "label": "judgment"}
{"text": "육아휴직 중 다른 회사에서 아르바이트해도 됩니까?", "label": "judgment"}

// doc_search — 문서/규정 검색
{"text": "연차 사용 규정 찾아줘", "label": "doc_search"}
{"text": "출장비 정산 관련 규정 어디 있어?", "label": "doc_search"}
{"text": "재택근무 신청 양식 좀 찾아줘", "label": "doc_search"}

// doc_generate — 문서 작성
{"text": "이번 분기 실적 보고서 작성해줘", "label": "doc_generate"}
{"text": "신규 프로젝트 제안서 만들어줘", "label": "doc_generate"}
{"text": "백엔드 개발자 채용공고 작성해줘", "label": "doc_generate"}

// meeting_generate — 회의록 작성
{"text": "오늘 회의 내용 회의록으로 정리해줘", "label": "meeting_generate"}
{"text": "방금 끝난 팀 회의 회의록 작성해줘", "label": "meeting_generate"}

// schedule_add — 일정 추가
{"text": "내일 오후 2시에 팀 회의 잡아줘", "label": "schedule_add"}
{"text": "금요일 오전 10시에 클라이언트 미팅 예약해줘", "label": "schedule_add"}

// schedule_view — 일정 조회
{"text": "오늘 일정 뭐 있어?", "label": "schedule_view"}
{"text": "이번 주 일정 보여줘", "label": "schedule_view"}

// general — 일반 질문
{"text": "안녕하세요", "label": "general"}
{"text": "좋은 아침이에요", "label": "general"}
```

### 4) Adversarial 테스트셋 (212문장)

모델이 헷갈리기 쉬운 **경계 문장** 위주로 구성:

```json

  // doc_search ↔ doc_generate 경계 (양식 찾기 vs 문서 작성)

  {"text": "출장 보고서 작성해줘", "label": "doc_generate"},
  {"text": "제안서 템플릿 있어?", "label": "doc_search"},

  // meeting_generate ↔ doc_generate 경계
  {"text": "회의 내용 정리해줘", "label": "meeting_generate"},
  {"text": "보고서 정리해줘", "label": "doc_generate"},

  // judgment ↔ doc_search 경계 (규정 질문 vs 규정 검색)
  {"text": "인센티브 지급 기준 좀 알려줘", "label": "judgment"},
  {"text": "연봉 계약서 사본 좀 찾아줘", "label": "doc_search"}
]
```

### 5) Blind 테스트셋 (70문장)

모델 개발에 **한 번도 사용되지 않은** 독립 데이터:
