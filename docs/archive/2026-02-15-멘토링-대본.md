## 2. 핵심 기능 3가지 (~1분)

저희 서비스의 핵심 기능은 세 가지입니다.

**첫 번째, 규정 판단입니다.** 사내 규정을 RAG(검색 증강 생성)로 검색하고, LLM이 근거 기반으로 판단해서 confidence 점수까지 함께 제공합니다.

**두 번째, 문서 자동 생성입니다.** 회의록, 보고서, 채용공고, 제안서 같은 문서를 템플릿 기반으로 AI가 작성해주고, 문서 요약이나 검색도 지원합니다.

**세 번째, 일정 관리입니다.** Google Calendar, Tasks, Gmail, Sheets까지 양방향 동기화해서, 채팅으로 일정을 등록하거나 조회할 수 있습니다.

사용자가 채팅창에 자연어로 질문하면, AI가 의도를 파악해서 세 가지 기능 중 적절한 Agent로 자동 라우팅하는 구조입니다.

## 3. 개발 전략 설명 (~2분)

**[화면공유: 멘토링 MD — 4. 개발 전략 섹션]**

개발 전략에 대해 설명드리겠습니다.

저희는 **"LLM API 먼저, sLLM은 나중에"** 전략을 쓰고 있습니다.

지금은 GPT나 Claude 같은 상용 LLM API로 전체 기능을 먼저 구현하고 있습니다. 실제로 동작하는 걸 확인하면서 입력과 출력의 형태를 확정한 다음에, 그 확정된 형태에 맞춰서 데이터를 수집하고, 마지막에 LoRA 파인튜닝해서 sLLM(소형 언어 모델)으로 모델만 교체하는 방식입니다.

파인튜닝을 지금 안 하고 나중에 하는 이유가 있는데요. 파인튜닝 데이터를 만들려면 정확한 입출력 포맷이 필요한데, 기능을 실제로 만들어보기 전에는 그 포맷이 계속 바뀝니다. 그래서 API로 기능을 먼저 완성하고, 포맷이 확정되면 그때 데이터를 모아서 파인튜닝하는 게 훨씬 효율적이라고 판단했습니다.

코드 구조도 이걸 염두에 두고 설계했는데, LLM을 호출하는 인터페이스가 공통 모듈로 분리되어 있어서, 나중에 sLLM으로 바꿀 때 모델 호출 부분만 교체하면 Agent 코드 자체는 수정할 필요가 없습니다.

참고로 sLLM 베이스 모델은 **Kanana-1.5-8B**으로 선정 완료했습니다. 경은이가 3개 모델을 벤치마크 비교했는데, 규정 해석 능력과 속도, JSON 형식 준수율 종합해서 Kanana가 1위였습니다.

## 4. 아키텍처 (~2분)

**[화면공유: 멘토링 MD — 외부 시스템 흐름도]**

아키텍처를 간단히 설명드리겠습니다.

먼저 외부 흐름입니다. 사용자가 브라우저에서 React 프론트엔드에 접속하고, 프론트엔드가 FastAPI 백엔드와 REST 또는 SSE(서버 전송 이벤트)로 통신합니다. 백엔드 뒤에 AI 엔진이 있고, AI 엔진은 LLM API와 Google API를 호출합니다. 데이터베이스는 PostgreSQL을 사용하고 있습니다.

**[화면공유: 멘토링 MD — 내부 AI 엔진 흐름도]**

내부 AI 엔진 흐름을 보시면, 사용자 입력이 들어오면 먼저 **Intent Classifier**가 7개 카테고리 중 하나로 의도를 분류합니다. 이건 klue/bert-base를 파인튜닝해서 만들었고, Eval F1 98.63%입니다.

분류된 의도가 **LangGraph 오케스트레이터**로 전달되면, confidence가 0.7 이상인 경우 해당 Agent로 라우팅됩니다. 규정 판단이면 Judgment Agent, 문서 관련이면 Document Agent, 일정이면 Schedule Agent, 일반 질문이면 LLM이 직접 응답합니다.

각 Agent의 응답은 **SSE 스트리밍**으로 실시간 토큰 단위로 프론트엔드에 전달됩니다.

## 5. 팀원별 성과 (~3분)

**[화면공유: 멘토링 MD — 6. 팀원별 주요 성과]**

1주일간 팀원 5명이 작업한 성과를 말씀드리겠습니다.

**저 신지용, PM 담당입니다.** Intent 학습 데이터 1,868개를 구축했고, BERT 파인튜닝을 버전 1.0부터 1.4까지 반복 개선했습니다. 추가로 3개 모델에 153번 하이퍼파라미터 그리드 서치 실험까지 완료해서, 최종 모델은 Eval F1 98.63%, Adversarial F1 91.67%를 달성했습니다. 오케스트레이터도 async 전환을 완료했고, main 브랜치 보호 설정도 했습니다.

**윤경은, AI 서브 담당입니다.** 3개 sLLM 모델 벤치마크를 돌려서 Kanana-1.5-8B을 베이스 모델로 선정했습니다. RAG 파이프라인을 8개 파일로 구현했는데, 하이브리드 검색(BM25 + Vector)에 RRF 융합, Reranker까지 갖추고 있고, 18개 테스트가 전부 통과입니다. 판단 Agent도 고도화해서 다중 규정 교차 판단, confidence 보정, SSE 스트리밍까지 구현했고, 테스트 27개 전부 통과입니다.

**진승언, AI 리드 담당입니다.** Docling과 PaddleOCR로 텍스트 추출기를 구현했고, Document Agent에서 문서 검색 의도를 감지해서 설명, 요약, 찾기로 분기합니다. Schedule Agent도 기본 구현을 완료해서, 자연어를 구조화된 JSON으로 파싱한 뒤 Google Calendar에 등록하거나 조회하는 기능이 동작합니다. RAG 최적화도 해서 Reranker 병목을 제거하고 응답 시간을 30초에서 수초로 줄였습니다.

**안혜빈, Backend 담당입니다.** PostgreSQL에 11개 테이블을 설계하고 Alembic 마이그레이션까지 완료했습니다. JWT 인증에 Google OAuth 소셜 로그인을 구현했고, Google Services 4종(Calendar, Tasks, Gmail, Sheets) 양방향 동기화도 완성했습니다. 문서 업로드 API도 11개 엔드포인트를 구현해서 PDF, DOCX, TXT 텍스트 추출까지 동작합니다.

**문지영, Frontend 담당입니다.** React로 10개 페이지, 63개 컴포넌트를 전부 구현했습니다. 다크 모드, 인쇄 기능, 글씨 크기 조절, 파일 드래그앤드롭, 대화 세션 관리까지 갖추고 있고, Google Calendar 실제 연동도 완료했습니다. ESLint 에러 0개, 반응형 디자인, 접근성 개선까지 해서 프론트엔드 품질이 상당히 탄탄합니다.

## 예상 질문 & 답변 (부록)

> 멘토님이 질문하시면 아래에서 찾아서 읽으면 됩니다

### Q1. "파인튜닝은 왜 안 하고 있어요?"

지금은 의도적으로 안 하고 있습니다. LLM API로 기능을 먼저 완성해서 입출력 형태를 확정한 다음에, 그 형태에 맞춰 데이터를 수집하고 파인튜닝하는 전략입니다. 파인튜닝 데이터를 만들려면 정확한 포맷이 필요한데, 기능이 안 잡힌 상태에서 데이터를 모으면 나중에 다 버려야 할 수 있어서요. 4단계에서 일괄 진행할 예정이고, 판단용 1,000건과 회의록 800건은 이미 원본 데이터가 확보되어 있습니다.

### Q2. "실제 동작하는 데모 있어요?"

아직 전체 파이프라인이 연결된 E2E 데모는 없습니다. 하지만 각 모듈은 개별적으로 동작하는 걸 확인했습니다. 판단 Agent는 테스트 27개 통과, RAG 파이프라인은 18개 통과, 프론트엔드는 10페이지 63컴포넌트가 빌드 성공하고, 일정 관리는 실제 Google Calendar 연동까지 됐습니다. 이번 주 안에 오케스트레이터 SSE 연동을 마치면 채팅으로 실제 질문하고 답변 받는 데모가 가능할 것 같습니다.

### Q3. "5명이서 어떻게 역할 나눴어요?"

저는 PM으로서 Intent 분류와 오케스트레이터, 프로젝트 관리를 맡고 있습니다. 경은이는 AI 서브로 RAG 파이프라인과 판단 Agent를, 승언이는 AI 리드로 문서 Agent와 파서 및 템플릿 시스템을 담당합니다. 혜빈이는 Backend 전체와 DB, 인증, Google Services를, 지영이는 Frontend 전체를 혼자 담당하고 있습니다. Git은 1인 1브랜치로 운영하고 있어서 충돌이 거의 없고, PR 방식으로 develop에 머지합니다.

### Q4. "sLLM 베이스 모델은 왜 Kanana?"

경은이가 3개 모델을 동일한 테스트셋 87개로 벤치마크했습니다. Kanana-1.5-8B, EXAONE-3.5-7.8B, Qwen3-8B 세 개를 비교했는데, 한국어 능력, 규정 해석 정확도, 판단 형식 준수율(JSON 유효율), 추론 속도 4가지 축으로 가중 평가한 결과 Kanana가 종합 점수 0.652로 1위였습니다. 특히 규정 해석과 속도에서 강점이 있었습니다.

### Q5. "RAG에서 Reranker를 비활성화했다고 했는데, 성능은 괜찮아요?"

승언이 Qdrant 파이프라인에서 Reranker를 돌리면 응답 시간이 15~30초까지 걸려서, RRF(역순위 융합) 방식으로 대체했습니다. RRF는 BM25와 Vector 검색 결과의 순위를 수학적으로 합산하는 방식인데, 정확도는 유지하면서 속도를 수초 수준으로 줄였습니다. 경은이의 판단 Agent용 RAG 파이프라인에서는 Reranker를 유지하고 있는데, 최종적으로 둘 중 어느 방향으로 통일할지는 성능 측정 후 결정할 예정입니다.

### Q6. "Intent 분류에서 Adversarial F1이 91%인데, 나머지 9%는 어떤 케이스예요?"

120개 Adversarial 테스트 중 10개가 오분류됐는데, 대부분 오타/축약어 4건, 극단적으로 짧은 입력 3건, 맥락에 의존하는 질문 2건, 카테고리 경계가 모호한 1건입니다. 이건 모델의 한계라기보다 전처리 단계에서 맞춤법 교정이나 초성 복원으로 해결할 수 있는 부분이고, 오케스트레이터 레벨에서 confidence가 낮으면 사용자에게 되물어보는 로직으로 보완할 계획입니다.
