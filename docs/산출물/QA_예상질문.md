K사 AI 연구센터 Data Scientist / M사 Technical Support Engineering


[아키텍처 & Agent]

Q. doc_retrieve에서 요약/검색/QA 분기 기준은?
A. 기본값은 검색으로 두었고, 요약은 키워드("요약해줘", "정리해줘")로 판별하고, 질문형이면서 RAG 점수가 0.5 이상이면 QA로 빠집니다. 검색이 가장 안전하기 때문에 기본값으로 두었습니다.

Q. 챗봇 대화를 어떻게 기억하나요?
A. 최근 5턴은 DB에서 원문 그대로 로드하고, 그 이전 대화는 sLLM이 요약해서 전달합니다. 토큰 제한 안에서 최근 맥락은 정확하게, 오래된 맥락은 요약으로 유지합니다. 모든 대화는 DB에 저장되어 있고 매 턴마다 필요한 만큼만 꺼내 씁니다.

Q. 왜 전부 원문으로 안 넣나요?
A. 토큰 제한과 비용 때문입니다. 대화가 길어지면 전부 넣을 수 없고, 요약하면 수천 자를 몇 백 자로 줄일 수 있습니다.

Q. Intent 분류를 왜 했나요?
A. 사용자가 뭘 원하는지 먼저 파악해야 맞는 Agent한테 보낼 수 있기 때문입니다. ONNX로 19ms 추론, API 비용 절감, softmax로 분류 유효율 100%가 구조적으로 보장됩니다.

Q. Intent 분류에 BERT를 쓴 이유는? LLM으로 하면 안 되나요?
A. 속도(19ms), 비용(0원), 안정성(유효율 100%) 세 가지입니다. LLM은 "모르겠다" 같은 무효 응답을 낼 수 있지만, BERT는 softmax로 항상 유효한 라벨을 출력합니다.

Q. Planner는 복합 질문을 어떻게 순차 처리하나요?
A. 멀티라벨로 복합 감지한 뒤 Planner가 서브쿼리로 분해하고, depends_on 의존성에 따라 순차적으로 각 Agent를 호출합니다. depends_on은 "이거 먼저 끝나야 다음 거 해"라는 순서표입니다.


[모델 선택 & 파인튜닝]

Q. 왜 Kanana를 선택했나요? 벤치마킹 해봤나요?
A. Qwen3, Kanana, EXAONE 세 모델을 동일 테스트셋으로 비교했습니다. JSON 유효율, intent 정확도, 의존성 정확도 등 5가지 지표로 평가했는데 성능은 비슷했습니다. 저희 서비스가 100% 한국어이기 때문에 한국어 토큰 효율이 가장 좋고 한국어 특화 사전학습이 된 Kanana를 선택했습니다.

Q. 한국어에 뛰어나다는 근거는?
A. 카카오에서 한국어 데이터 비중을 높여 사전학습한 모델입니다. 규정 텍스트나 문서 양식처럼 한국어 특유의 표현이 많은 입력에서 토큰 효율과 자연스러운 출력이 더 좋았습니다.

Q. LoRA r=16과 r=32를 다르게 쓴 이유는?
A. 판단/요약은 출력이 짧고 구조가 단순해서 r=16이면 충분했고, 문서생성은 필드가 많고 출력이 길어서 r=32로 파라미터를 더 주었습니다. 실험으로 확인한 결과입니다.

Q. 과적합 해소를 위해 모델 크기만 키웠나요?
A. 둘 다 했습니다. 112M에서 338M으로 모델 교체와 동시에 GPT Knowledge Distillation으로 학습 데이터도 확대했습니다. 오답 타겟 보강을 3라운드 반복해서 최종 91%를 달성했습니다.

Q. RAG 학습 시 성능 떨어진 이유는?
A. RAG 검색 노이즈가 정답 라벨과 모순을 일으킵니다. 정답이 yes인데 RAG가 관련 없는 규정을 가져오면 모델이 no로 학습하게 됩니다. 그래서 학습은 정답 규정을 하드코딩으로 넣고, 서빙 때만 RAG를 사용합니다.

Q. 5-factor Confidence 보정 가중치는 어떻게 정했나요?
A. LLM raw 60%, RAG 점수 25%, 규정 커버리지 15%입니다. 초기 균등 가중치에서 출발해서 오답 분석하며 LLM 과신 패턴이 많아 RAG와 규정 쪽 보정 비중을 높였습니다.

Q. False Fill 17.9%를 더 줄일 방법은?
A. v4 실험에서 채움률을 올리면 환각도 같이 증가하는 트레이드오프를 확인했습니다. 현재는 안정성 우선으로 v3를 유지하고, 학습 데이터 다양화로 개선할 예정입니다.

Q. 복합 질문 3-step이 66.7%인데 왜 낮은가요?
A. 8B 모델의 멀티스텝 추론 한계입니다. 1-step은 91.3%로 높지만 3개 인텐트를 동시에 분해하면 정확도가 떨어집니다. 데이터 확장이나 모델 스케일업으로 개선할 계획입니다.

Q. 분류 유효율 100%가 뭔가요?
A. 모델이 정해진 카테고리 중 하나로 답한 비율입니다. Base 모델은 자기 맘대로 답해서 85%였고, LoRA 파인튜닝으로 출력 형식을 학습시켜 100%가 됐습니다.

Q. Reranker가 +5.7초인데 실서비스에서 허용 가능한가요?
A. 정답이 항상 1순위로 올라오는 MRR 0.952의 가치가 크기 때문에 채택했습니다. 향후 빈출 규정 캐싱과 모델 경량화로 속도를 개선할 계획입니다.


[문서 생성 과정]

Q. 문서가 다양할텐데 어떻게 필드를 추출하나요?
A. 템플릿 업로드 시 필드를 자동 추출하고, 문서 생성 시 sLLM이 사용자 입력과 필드 명세를 받아 JSON으로 각 필드를 채워서 문서를 완성합니다. DOCX는 결국 테이블, 헤딩, 본문 세 가지로 구성됩니다. 테이블에서 라벨 옆에 빈칸이 있으면 필드로 추출하고, 헤딩(30자 이하)과 본문의 "필드명:" 패턴은 보조로 사용합니다.

Q. 라벨은 어떻게 라벨이라고 인식하나요?
A. 20자 이하의 한글/영문 텍스트이면서 옆 셀이 비어있으면, 그게 라벨과 입력 필드의 쌍입니다. "구분", "합계" 같은 테이블 구조 단어는 제외합니다. 라벨이 아닌 것들로는 순수 숫자("123"), 테이블 구조용 단어("구분","비고","합계"), 20자 초과 본문 텍스트, 빈칸 플레이스홀더("년/월/일" 등)가 있습니다.

Q. description은 어떻게 뽑나요?
A. 135개 한글-영어 매핑 사전에 있으면 사전 설명을 쓰고, 없는 필드는 LLM한테 한 번에 물어봐서 보강합니다. 업로드 때 1번만 실행됩니다.

Q. 복잡한 표 양식은요?
A. 현재 한계점으로 인식하고 있습니다. 단순한 라벨-빈칸 구조는 잘 잡지만, 셀 병합이 복잡한 표는 추출이 어렵습니다. 학습 데이터를 다양화해서 개선할 계획입니다.

Q. 새로운 양식도 되나요?
A. 네, 커스텀 템플릿 업로드 기능이 있습니다. 사용자가 DOCX를 올리면 자동으로 필드를 추출하고, 바로 그 양식으로 문서 생성이 가능합니다.


[인프라 & 배포]

Q. 실제 배포 환경은?
A. AWS EC2에 Backend+Frontend, RunPod A100에 vLLM 서빙, Qdrant Cloud에 벡터DB입니다. LoRA 어댑터는 GPU 재시작 없이 약 100ms 핫스왑으로 교체됩니다.

Q. vLLM 한글 깨짐 문제 해결법?
A. LORA_DTYPE을 bfloat16으로 강제하면 베이스 모델과 dtype이 불일치해서 한글 토큰이 깨집니다. auto로 변경하면 베이스 모델에 맞춰 자동 결정되어 해결됩니다.

Q. sLLM 서버 다운 시?
A. OpenAI API fallback이 구현되어 있습니다. vLLM 호출 실패 시 자동으로 GPT API로 전환되어 서비스 중단 0건을 유지합니다.

Q. Google Workspace OAuth 토큰 관리?
A. Google OAuth 2.0으로 인증 후 AES-256으로 암호화하여 DB에 저장합니다. 리프레시 토큰으로 자동 갱신하며, 5종을 단일 OAuth 플로우로 처리합니다.

Q. SSE State 손실 문제?
A. React에서 SSE 이벤트가 빠르게 들어오면 state 업데이트가 배칭되어 중간 데이터가 손실되었습니다. Ref 기반 배열 관리로 전환해서 해결했습니다.

Q. 데이터 보안은?
A. 사내 규정과 문서가 외부 API로 전송되지 않습니다. sLLM 자체 서빙 + S3 문서 저장 + JWT 인증 + AES-256 암호화를 적용했습니다.


[공통]

Q. GPT-4o 대비 sLLM 장단점?
A. 장점은 과금 0원, 데이터 보안, 도메인 특화입니다. 단점은 응답 속도 7.3초(GPT는 2.4초)입니다. 템플릿 품질은 동등(100/100)합니다.

Q. 이 프로젝트의 실제 사용 타겟은?
A. 제조/IT 중견기업의 경영지원팀입니다. 규정 확인, 문서 작성, 일정 관리가 일상 업무의 대부분을 차지하는 직군입니다.

Q. 4명이서 이걸 다 했나요?
A. PM(지용)은 오케스트레이터 + Intent 분류 + 문서 Agent, FE/AI(지영)은 React UI + SSE + Intent 멀티라벨 + Planner LoRA, BE(혜빈)은 FastAPI + DB + Google 5종 + 일정 Agent, AI(경은)은 판단 Agent + RAG + LoRA 파인튜닝을 담당했습니다.

Q. ROUGE-L / BERTScore F1 / JSON 유효율이 뭔가요?
A. ROUGE-L은 정답과 생성 텍스트의 단어 겹침(키워드 채점), BERTScore F1은 의미 유사도(뜻이 맞으면 OK), JSON 유효율은 생성된 JSON이 파싱 가능한 비율(서류 양식 오류 검사)입니다.

Q. JSON 유효율을 어떻게 올렸나요?
A. 가장 효과적인 건 structured output(guided_json)으로 문법 자체를 강제하는 것이고, 그 다음은 학습 데이터를 깨끗하게 만드는 것입니다. 프롬프트 강화와 temperature 낮추기도 병행했습니다.
