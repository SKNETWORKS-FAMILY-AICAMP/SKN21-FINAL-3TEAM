## 1. 프로젝트 개요

### 한 줄 소개
**WorkFlow Agent (듀듀)** — LangGraph 기반 멀티 Agent 업무 자동화 시스템. 사내 규정 판단, 문서 분석/생성, 일정 관리를 AI Agent가 처리합니다.

### 기술 스택

| 영역 | 기술 |
|------|------|
| AI | LangGraph, GPT/Claude API (현재) → vLLM + LoRA (4단계), Qdrant + BM25 + bge-reranker |
| Backend | FastAPI + SSE, PostgreSQL 16, SQLAlchemy + Alembic, JWT, Google OAuth 2.0 |
| Frontend | React (Vite), Zustand, TanStack Query, Tailwind + shadcn/ui, FullCalendar |
| Infra | AWS (EC2+S3+RDS), Docker, GitHub Actions, RunPod (A100) |

### 팀 구성

| 이름 | 역할 | 핵심 담당 |
|------|------|----------|
| 신지용 | PM | Intent 분류 + LangGraph 오케스트레이터 + SSE + 배포 |
| 윤경은 | AI 서브 | 판단 Agent + RAG Pipeline + Reranker + vLLM 서빙 + LoRA v1 |
| 진승언 | AI 리드 | 문서 Agent + Document Parser + Template Engine + LoRA v2 |
| 안혜빈 | Backend | DB + 인증 + API + 일정 Agent + Google Services 통합 (5개 서비스) |
| 문지영 | Frontend | React UI 전체 (10개 페이지, 63개 컴포넌트, 다크모드, 인쇄, 애니메이션) |

## 2. 전체 진행률

### 6단계별 현황

| 단계 | 내용 | 진행률 | 상태 |
|------|------|:------:|:----:|
| 1단계 | 설계 및 환경 세팅 | **100%** | 완료 |
| 2단계 | 기반 개발 + LLM API 연동 | **95%** | 거의 완료 |
| 3단계 | Agent 개발 + 핵심 기능 | **75%** | **진행 중** |
| 4단계 | 데이터 수집 + 파인튜닝 | **10%** | Intent 데이터만 완료 |
| 5단계 | 통합 및 테스트 | **5%** | E2E 일부 작성 |
| 6단계 | 배포 및 마무리 | **10%** | Docker 구성 완료, AWS 미착수 |

### 개발 전략: LLM 먼저 → sLLM은 나중에

```
1. LLM API(GPT/Claude)로 전체 기능 먼저 구현        ← 현재 여기
2. 실제 동작 확인하면서 input/output 형태 확정
3. 확정된 형태에 맞춰 데이터 수집
4. 파인튜닝 → sLLM(vLLM) 교체 (모델만 갈아끼우면 됨)
```

## 5. 멘토 논의 사항 (1): Intent 분류 방식

### 현재 상황

| 항목 | 수치 |
|------|------|
| 모델 | klue/bert-base (fine-tuned) |
| 학습 데이터 | 1,916개 (7카테고리) |
| Eval F1 | 98.63% |
| Adversarial F1 (212문장) | **90.07%** (전처리 적용) |
| Blind F1 (70문장) | 95.62% |
| 추론 속도 | **7.48ms** (GPU), ~14ms (CPU) |
| 비용 | **$0** (로컬 추론) |

### 문제: Overconfident Error

- BERT 오분류 중 **57.7%가 confidence > 0.8인 상태에서 틀림** (overconfident)
- 예: "연차 규정 알려줘" → BERT가 doc_search(0.91)로 분류 → 실제는 judgment
- **confidence 기반 폴백만으로는 해결 불가** (높은 confidence에서 틀리므로)

### 현재 대응 (이미 구현)

1. **KNOWN_OVERRIDES**: 반복 오분류 패턴 5개를 규칙으로 보정 (정규식 매칭)
2. **전처리 파이프라인**: 맞춤법 교정 + 초성 복원 + 슬랭 정규화
3. **복합질문 분해**: 3중 AND 신호로 복합 감지 → LLM으로 분해 후 각각 BERT 분류
4. **저신뢰도 되묻기**: confidence < 0.7이면 top-3 후보 제시하여 사용자에게 확인

### 멘토에게 논의할 3가지 옵션

| 옵션 | 방식 | 장점 | 단점 |
|------|------|------|------|
| **A. sLLM 유지 + 오케스트레이터 검증** | BERT 분류 후, 오케스트레이터에서 맥락 기반 검증 (이전 대화 참조) | 속도 유지 (7ms), 비용 $0, 기존 코드 활용 | overconfident 오분류 일부 잔존 |
| **B. sLLM + LLM 하이브리드** | BERT 1차 분류 → confidence < 임계값 or KNOWN 패턴 시 LLM 2차 분류 | 정확도 극대화, 대부분은 BERT로 빠르게 처리 | LLM 호출 비용/지연 (임계값 조정 필요) |
| **C. LLM 단독** | GPT/Claude로 Intent 분류 | 최고 정확도 (GPT F1 97.5% @70문장) | 속도 ~450ms (68배 느림), API 비용 |

### PM 의견

- **옵션 A 선호** — 현재 Adv F1 90%이고, overconfident 패턴은 KNOWN_OVERRIDES로 점진적 추가 가능
- 옵션 B는 임계값 설정이 어려움 (overconfident error가 주 문제이므로 폴백 트리거 자체가 안 됨)
- **질문**: 옵션 A로 충분한가? 아니면 비용을 감수하고 B로 가야 하는가?

### 논의 포인트

**Q1. 데이터 수집 전략**
- 현재 확보: Intent 1,916 + 판단 1,000 + 회의록 800 = **3,716개**
- 미수집: Q&A 500 + 문서계열 900 = **1,400개**
- 수집 방법: GPT/Claude로 초안 생성 → 사람 검증 (Intent 데이터와 동일 방식)
- **질문**: 데이터 품질 vs 양 — 1,500개 수준이면 LoRA로 충분한가?

**Q2. LoRA 학습 계획**
- QLoRA 4-bit (VRAM 절약: A100 40GB로 8B 모델 학습 가능)
- 학습 환경: RunPod A100
- 평가: 검증 15% 별도 분리, 학습에 사용하지 않음
- **질문**: Kanana-1.5-8B가 최선인가? 벤치마크 결과 종합 0.652로 아직 낮은 편

**Q3. sLLM 교체 타이밍**
- 현재 전략: LLM API로 기능 완성 → I/O 확정 → 데이터 수집 → 파인튜닝 → 교체
- 코드 구조: `ai/llm/factory.py`에서 `LLM_PROVIDER=vllm`으로 바꾸면 즉시 전환
- vLLM Provider 이미 구현 완료 (`ai/serving/vllm_client.py`)
- **질문**: 중간발표 전에 LoRA v1(판단)이라도 시도해볼 가치가 있는가? (데이터 1,000개 이미 확보)
