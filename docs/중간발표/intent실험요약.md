# Intent 분류 실험 스토리라인 (7-Stage)

## 배경: 왜 이 실험을 했나

사용자가 "연차 규정 알려줘"라고 치면 → Judgment Agent로,
"보고서 만들어줘"라고 치면 → Document Agent로 보내야 함.

**라우팅을 틀리면 = 답변 자체가 틀림** → Intent 분류기 정확도가 시스템 전체 품질을 결정.

8개 intent: `judgment`, `doc_search`, `doc_generate`, `doc_summary`, `doc_qa`, `schedule_add`, `schedule_view`, `general`

---

## Stage 1: 데이터 만들기
> "좋은 모델은 좋은 데이터에서 나온다"

- GPT-4o + Claude Sonnet 4 **두 개 LLM**으로 데이터 생성 (한쪽 편향 방지)
- 기본 데이터 2,299개 + **경계 쌍 600개** (헷갈리기 쉬운 쌍 집중 생성)
- 적대적(adversarial) 테스트셋 450개 별도 제작 — 일부러 어렵게 만든 문장
- Train 2,327 / Val 285 / Test 286 분할 (중복 0건 QA 통과)

---

## Stage 2: 모델 3개 동일 조건 비교
> "어떤 모델이 제일 잘 맞나?"

| 모델 | Val F1 | 크기 | 특징 |
|------|:------:|:----:|------|
| **KoELECTRA** | **98.25%** | 112.9M | 토큰 교체 감지 방식 |
| BERT | 97.80% | 110.6M | 한국어 NLU 표준 |
| DistilKoBERT | 94.98% | 28.4M | 경량화 모델 |

→ **KoELECTRA 1등**, 동일 조건에서 가장 높음

---

## Stage 3: 하이퍼파라미터 최적화
> "KoELECTRA를 최대로 끌어올려보자"

- 32가지 조합 Grid Search (epochs/lr/batch)
- **Best: ep10, lr3e-5, bs16 → Val F1 98.97%**
- Baseline(98.25%) → Best(98.97%): **+0.72%p만 상승**
- **교훈: 데이터 품질 > 하이퍼파라미터** (HP 튜닝 효과 제한적)

---

## Stage 4: 실전 테스트 (적대적 데이터 450개)
> "실험실에선 다 잘 되지만, 진짜 어려운 입력에서는?"

| 모델 | Test F1 | **Adv F1** | 속도 |
|------|:------:|:--------:|:---:|
| **KoELECTRA** | 97.26% | **86.04%** | **7.9ms** |
| BERT | 97.56% | 85.17% | 10.4ms |
| DistilKoBERT | 96.45% | 79.26% | 2.8ms |

- 전처리(맞춤법교정 등) 시도 → **효과 없음** (Ablation A~E 전부 동일)
- **KoELECTRA 최종 선택** (정확도 1등 + 속도 24% 빠름)

---

## Stage 5: 오분류 분석 + 타겟 보강
> "틀린 63건을 분석해서 약점을 보강하자"

오분류 63건 패턴:
- short_text 47건 (짧은 입력)
- **overconfident 42건** (90% 이상 확신하면서 틀림) ← 큰 문제
- doc_qa→doc_search 혼동 10건 (제일 많은 혼동 쌍)

**약점 타겟 보강 98개 추가 → 재학습:**
- Adv F1: 86.04% → **87.84% (+1.80%p)**
- doc_qa: 71.0% → **78.9% (+7.9%p)** — 최대 개선

---

## Stage 6: Label Smoothing (과신뢰 해소)
> "틀릴 때 자신감을 낮춰서, 안전하게 걸러내자"

Stage 5에서 발견한 핵심 문제: **42건이 90% 확신하면서 틀림** → threshold로 못 잡음

Label Smoothing 0.1 적용 결과:
- 정확도는 거의 동일 (Adv F1 -0.26%p)
- **과신뢰 오분류: 42건 → 13건 (-69%)**
- confidence threshold를 0.7 → **0.85**로 올림
- 0.85 미만이면 "되묻기(clarify)" → 안전하게 처리

---

## Stage 7: 라벨 리뷰 + 시나리오 100개
> "진짜 모델이 못하는 건지, 라벨이 잘못된 건지 구분하자"

doc_qa 오분류 27건 수동 분석:
- 37% 모델이 진짜 틀림
- 33% 인간도 판단 곤란 (라벨 애매)
- **30% 모델이 맞는데 라벨이 틀림**
- → **오류의 63%가 모델 문제가 아님** (실질 성능 ~85%)

시나리오 100문장 테스트:
- normal(표준): **100%** — 일반 입력은 완벽
- short(초단문): 93.3%
- boundary(경계): 78.8%
- informal(비속어): 76.0% — 최약점

25개 소량 보강 시도 → 효과 없음 → **최종 모델은 Stage 6 유지**

---

## 한 줄 스토리

```
데이터 생성 → 모델 비교(KoELECTRA) → HP 튜닝(효과 적음)
→ 실전 평가 → 오분류 분석+보강(+1.8%p) → Label Smoothing(과신뢰 -69%)
→ 라벨 검증(오류 63%가 라벨 문제) → 최종 87.58%
```

**핵심 교훈**: `데이터 품질 > 하이퍼파라미터 > 모델 아키텍처`
