## 슬라이드 1: 문제 정의 + 프로젝트 소개 (1:30)

### 비주얼

- **상단**: 문제 상황 일러스트 (직원이 규정집 뒤지는 모습 vs 듀듀에 물어보는 모습)
- **중단**: 듀듀 로고 + "LangGraph 기반 멀티 Agent 업무 자동화" 한 줄 소개
- **하단**: 핵심 기능 4가지 아이콘 카드 + 팀 소개

### 대본

> 안녕하세요. 여러분, 혹시 회사에서 "이거 규정 위반이야?" 싶을 때 규정집 뒤져보신 적 있으신가요?
>
> 규정은 수십 개 문서에 흩어져 있고, 어떤 조항이 적용되는지 찾는 데만 30분. 일정 등록하려면 캘린더 열고, 회의록 쓰려면 또 다른 도구를 열고. **도구를 쓰는 시간이 일하는 시간보다 길어지는** 문제, 저희가 해결하려고 합니다.
>
> 저희 프로젝트 "듀듀"는 **LangGraph 기반 멀티 Agent 업무 자동화 시스템**입니다. 챗봇에 자연어로 요청하면, AI가 의도를 파악해서 적절한 Agent로 연결하고, 결과를 돌려줍니다.
>
> 핵심 기능 4가지입니다.
> 1. **규정 판단** — "인턴에게 AWS 접근 줘도 돼?" → RAG로 규정 검색 후 근거와 함께 판단
> 2. **문서 관리** — 검색, 생성, 요약, Q&A
> 3. **일정 관리** — 자연어로 일정 등록 → Google Calendar + Meet + Gmail + Tasks + Sheets 5대 서비스 자동 연동
> 4. **회의록 생성** — 회의 내용 입력하면 자동 정리
>
> 저희 팀은 PM, AI 2명, 백엔드, 프론트엔드 — 5명이 역할을 나눠 개발하고 있습니다.

### 발표자 노트

## 슬라이드 2: 시스템 아키텍처 (2:00)

### 비주얼

- **좌측 2/3**: 파이프라인 다이어그램
  ```
  사용자 입력 → Frontend (React) → Backend (FastAPI + SSE)
                                       ↓
                              Orchestrator (LangGraph)
                                       ↓
                              Intent Classifier (KoELECTRA, 7.9ms)
                                       ↓
                    ┌──────────┬──────────┬──────────┐
                 Judgment   Document   Schedule   General
                 Agent      Agent      Agent      Response
                    │          │          │          │
                 RAG+LLM    LLM      Google API    LLM
                    └──────────┴──────────┴──────────┘
                                       ↓
                              SSE 스트리밍 응답 → UI 렌더링
  ```
- **우측 1/3**: 기술스택 3-layer 아이콘
  - AI Layer: LangGraph, KoELECTRA, Qdrant, GPT/Claude API
  - Backend Layer: FastAPI, PostgreSQL, JWT, Google OAuth
  - Frontend Layer: React, Zustand, TanStack Query, Tailwind

### 대본

> 전체 아키텍처입니다. 핵심은 **"분류 → 라우팅 → 전문 Agent 처리 → 스트리밍 응답"** 이 파이프라인입니다.
>
> 사용자 입력이 들어오면, **오케스트레이터**가 가장 먼저 받습니다. 오케스트레이터 안의 **Intent Classifier**가 입력을 8개 의도 중 하나로 분류합니다. KoELECTRA를 파인튜닝한 모델이고, 추론 7.9ms — 사용자가 지연을 느끼지 못하는 수준입니다.
>
> 분류 결과에 따라 4개 Agent 중 하나로 라우팅합니다.
> - **Judgment Agent**: RAG로 사내 규정 270개 청크 검색 → LLM이 근거와 함께 판단
> - **Document Agent**: 문서 검색, 생성, 요약, Q&A — 4가지 서브 기능
> - **Schedule Agent**: Google Calendar, Tasks, Gmail, Meet, Sheets — 5대 서비스 오케스트레이션
> - **General**: 일반 대화 처리
>
> 여기서 중요한 설계 원칙이 있습니다. confidence가 0.85 미만이면 Agent로 보내지 않고, **"혹시 이런 뜻이세요?"** 하고 top-3 후보를 제시해서 되묻습니다. **모르면 되묻는 안전장치**입니다.
>
> 응답은 **SSE(Server-Sent Events)** 로 토큰 단위 실시간 스트리밍됩니다. 사용자가 기다리지 않고 바로 답변이 흘러나오는 UX입니다.
>
> 기술스택은 3-layer로 구성됩니다.
> - AI: LangGraph + Qdrant + GPT/Claude API (현재) → vLLM + LoRA (추후)
> - Backend: FastAPI + PostgreSQL + JWT + Google OAuth 2.0
> - Frontend: React + Zustand + Tailwind + FullCalendar

### 발표자 노트

- 다이어그램 위에서 아래로 따라가면서 설명
- "7.9ms" 강조 — 실시간성 어필
- "모르면 되묻는다" — clarify 라우팅이 차별화 포인트
- 기술스택은 빠르게 훑고 넘어가기

## 슬라이드 5: 기술 Deep-Dive 1 — Intent 분류 (2:00)

### 비주얼

- **좌측 상단**: `baseline_comparison.png` (3모델 비교 바 차트)
- **우측 상단**: `stage6_comparison.png` (Stage별 개선 비교)
- **중단**: 실제 분류 예시 테이블 (3개 입력 → 분류 결과 + confidence)
  | 입력 예시 | 분류 결과 | Confidence | 판정 |
  |-----------|-----------|:---------:|:----:|
  | "다음 주 수요일 2시에 팀 회의 잡아줘" | schedule_add | 0.94 | ✅ 정확 |
  | "출장비 정산 규정이 어떻게 되는지 문서 찾아줘" | doc_search | 0.92 | ✅ 경계 케이스 |
  | "휴가 규정에 대해 판단해줄 수 있어?" | doc_qa | 0.83 | ⚠️ clarify 발동 |
- **하단**: 3가지 교훈 요약 패널 (아이콘 + 한 줄 설명)
- **우측 하단**: 최종 지표 박스: `F1 87.84% | 7.9ms | 과신뢰 -69%`

### 대본

> Intent 분류 실험에 대해 말씀드리겠습니다. 사용자 입력을 8개 의도로 분류하는 게이트키퍼입니다. 이걸 잘못하면 엉뚱한 Agent가 답변합니다.
>
> 3가지 모델을 비교했습니다. KoELECTRA, BERT, DistilKoBERT — 동일 조건에서 테스트했더니, **일반 데이터에서는 셋 다 95% 이상으로 비슷**합니다. 하지만 의도적으로 어렵게 만든 **Adversarial 테스트 450문장**에서 진짜 실력이 드러납니다. KoELECTRA가 86%, BERT 85%, DistilKoBERT 79%. KoELECTRA를 선택했습니다.
>
> 실제 예시를 보시면 — "다음 주 수요일 2시에 팀 회의 잡아줘"는 schedule_add로 정확히 분류합니다. confidence 0.94.
>
> 까다로운 경계 케이스입니다. "출장비 정산 규정이 어떻게 되는지 **문서 찾아줘**" — '규정'이라는 단어가 있어서 judgment으로 갈 수도 있지만, 모델은 '문서 찾아줘'에 주목해서 **doc_search로 정확히 분류**합니다.
>
> 반면 "휴가 규정에 대해 판단해줄 수 있어?"는 judgment이 맞지만, confidence가 0.83으로 기준(0.85) 미만입니다. 이때 **clarify 라우팅이 발동**해서 "혹시 규정 판단인가요? 문서 Q&A인가요?" 하고 되묻습니다. 틀리더라도 사용자에게 확인받는 구조입니다.
>
> 이런 시나리오 테스트 100문장을 돌렸을 때, **표준 업무 입력은 100%**, 전체 85%입니다. 어려운 경계 입력에서 틀리더라도 clarify가 잡아줍니다.
>
> 7단계 실험에서 얻은 **3가지 교훈**입니다.
>
> **첫째, 데이터 품질이 하이퍼파라미터보다 중요합니다.** 32가지 HP 조합 탐색 → +0.72%. 오분류 분석 후 타겟 보강 98개 → **+1.8%**. 10배 차이입니다.
>
> **둘째, "확신 있게 틀리는 것"이 가장 위험합니다.** 오분류 63건 중 42건이 confidence 90% 이상인데 틀리는 과신뢰였습니다. Label Smoothing으로 **과신뢰 오류 69% 감소**시켰습니다.
>
> **셋째, 모델 탓만 하지 말고 라벨을 의심하라.** 가장 약한 doc_qa 오분류를 수동 검토했더니 **63%가 라벨 자체 문제**였습니다.
>
> 최종: **Adversarial F1 87.84%, 추론 7.9ms, 과신뢰 -69%.**

### 발표자 노트

- **예시 먼저 → 교훈 나중** 순서로 진행 (구체→추상)
- 경계 케이스 "출장비 정산 규정" 예시에서 '규정' 단어를 손가락으로 가리키며 설명
- clarify 라우팅 예시로 "틀려도 안전한 구조" 강조
- "3가지 교훈"은 빠르게 훑기 (각 10초)
- 시간 약 2분 — 이전 v2의 4슬라이드를 1슬라이드로 압축한 핵심

## 슬라이드 6: 기술 Deep-Dive 2 — RAG + 환각 방지 (1:30)

### 비주얼

- **좌측**: RAG 파이프라인 다이어그램
  ```
  사용자 질문
      ↓
  ┌─────────────────┐
  │ BM25 검색       │  → Top 15 (키워드 매칭)
  │ Vector 검색     │  → Top 15 (의미 유사도, Qdrant)
  └────────┬────────┘
           ↓
  RRF(Reciprocal Rank Fusion) 합산 → Top 20
           ↓
  source 필터 (regulations / documents)
           ↓
  Top K 전달 → LLM 판단/답변
  ```
- **우측**: 4층 환각 방지 가드 다이어그램
  ```
  ┌─ Layer 1: 키워드 매칭 (인용 cross-check) ──────┐
  │  LLM이 인용한 조항 ↔ RAG 검색 결과 대조         │
  ├─ Layer 2: 조항 존재 검증 ──────────────────────┤
  │  "제8조" 인용 → Qdrant에서 실제 존재 validate   │
  ├─ Layer 3: 판단 카테고리 제한 ──────────────────┤
  │  yes/no/conditional/no_regulation 외 → reject  │
  ├─ Layer 4: confidence 보정 ─────────────────────┤
  │  LLM(60%) + RAG점수(25%) + 커버리지(15%)       │
  │  - 환각 감점 - 조항 미존재 감점                  │
  └────────────────────────────────────────────────┘
  ```

### 대본

> 저희 시스템의 **최강 차별화 포인트**, RAG 파이프라인과 환각 방지 체계입니다.
>
> 먼저 RAG입니다. 단순 벡터 검색만 하면 키워드를 놓칩니다. 저희는 **Hybrid Search** — BM25 키워드 검색과 Qdrant 벡터 검색을 동시에 수행하고, **RRF(Reciprocal Rank Fusion)** 으로 점수를 합산합니다. 키워드 매칭과 의미 유사도를 둘 다 잡습니다.
>
> 더 중요한 건 **환각 방지**입니다. LLM은 그럴듯한 거짓말을 합니다. 규정 판단에서 환각은 치명적입니다. 그래서 **4층 가드 시스템**을 구축했습니다.
>
> **1층 — 키워드 cross-check.** LLM이 "제8조에 따르면..."이라고 인용하면, 그 제8조가 RAG 검색 결과에 실제로 있는지 대조합니다.
>
> **2층 — 조항 존재 검증.** Qdrant에서 해당 조항이 실제 존재하는지 validate합니다. 없으면 환각 의심 플래그.
>
> **3층 — 카테고리 제한.** 판단 결과가 yes/no/conditional/no_regulation 4가지 외의 값이면 자동 reject합니다.
>
> **4층 — confidence 보정.** LLM이 스스로 매긴 점수를 그대로 쓰지 않습니다. RAG 검색 품질, 규정 커버리지, 환각 탐지 결과를 종합해서 보정합니다. LLM 60%, RAG 점수 25%, 커버리지 15%로 가중 합산하고, 환각이 탐지되면 감점합니다.
>
> 이 4층 가드가 **일반 RAG 챗봇과 저희를 구분하는 핵심**입니다.

### 발표자 노트

- 4층을 손가락으로 하나씩 세면서 설명

## 예상 Q&A (6개)

### Q1: 왜 BERT가 아니라 KoELECTRA인가요?

> 동일 크기(111M)에서 KoELECTRA가 Adversarial F1 0.87%p 높고 추론 24% 빠릅니다. 통계적 유의차(McNemar p>0.05)는 없지만 "동급"이라는 뜻이고, 동급이면 빠르고 강건한 쪽을 선택하는 게 합리적입니다. ELECTRA의 토큰 교체 감지(RTD) 사전학습이 짧은 한국어 문장에서 미세한 의미 차이를 잡는 데 유리했습니다.

### Q2: 환각 방지 4층이 구체적으로 어떻게 동작하나요?

> 예를 들어 LLM이 "정보보안 규정 제8조에 따라..."라고 답했다고 합시다.
> - **1층**: "제8조"가 RAG 검색 결과에 있는지 텍스트 매칭 → 없으면 환각 의심
> - **2층**: Qdrant 벡터DB에서 "제8조" 존재 여부를 별도 validate
> - **3층**: 판단 결과가 yes/no/conditional/no_regulation 4가지 중 하나인지 확인 → 아니면 reject
> - **4층**: confidence를 LLM(60%)+RAG점수(25%)+커버리지(15%)로 재계산, 환각 탐지 시 감점
>
> 실제 코드가 `judgment_agent.py`에 구현되어 있고, 함수별로 분리되어 테스트 가능합니다.

### Q3: Adversarial 87%면 실서비스에서 13%가 틀리나요?

> Adversarial은 의도적으로 어렵게 만든 데이터입니다. 일반 입력(Val)에서는 **98.9%**, 100문장 시나리오 테스트에서 표준 업무 입력은 **100%**입니다. 어려운 경계 입력에서 틀리더라도, confidence 0.85 미만이면 **clarify 라우팅**이 "혹시 이런 뜻이세요?"라고 되묻기 때문에, 사용자가 체감하는 오류는 훨씬 적습니다.

### Q4: RAG에서 BM25+Vector Hybrid를 쓰는 이유는?

> 벡터 검색만 하면 **키워드를 놓칩니다**. 예를 들어 "제3조 2항"처럼 조항 번호를 정확히 지정하면, 의미 유사도로는 잡기 어렵지만 BM25 키워드 매칭으로는 바로 잡힙니다. 반대로 "인턴 권한 관련 규정"처럼 의미적 질문은 벡터 검색이 강합니다. **RRF(Reciprocal Rank Fusion)** 로 두 결과를 합산하면 양쪽 장점을 모두 가져갑니다.

### Q5: LLM API에서 sLLM으로 교체하면 성능이 떨어지지 않나요?

> Intent 분류기는 이미 sLLM(KoELECTRA)으로 동작 중이고 성능이 검증됐습니다. 판단/문서 Agent는 LLM API로 input/output 형태를 확정한 상태에서 파인튜닝하기 때문에, 동일 품질을 목표로 학습합니다. Base 모델로 **Kanana-1.5-8B**을 선정했고 (벤치마크 종합 0.652), 교체 후 성능 비교 실험도 진행할 예정입니다. Factory 패턴 덕분에 provider만 바꾸면 되므로 **A/B 비교도 쉽습니다**.

### Q6: Google 5대 서비스 통합은 어떻게 관리하나요?

> **GoogleBaseService**라는 공통 베이스 클래스가 있고, Calendar/Tasks/Gmail/Sheets 서비스가 이를 상속받습니다. 토큰 관리, scope 처리, 에러 핸들링, 재인증 로직이 공통화되어 있습니다. OAuth 2.0 통합 인증에서 필요한 scope를 한 번에 획득하고, `oauth_tokens` 테이블에 저장합니다. **schedule_service.py**가 4개 서비스를 오케스트레이션해서, "일정 등록" 한 명령이 Calendar 등록 → Meet 링크 생성 → Tasks 동기화 → Gmail 알림 → Sheets 기록까지 연쇄 동작합니다.
