> 윤경은 (AI Engineer) | Kanana-1.5-8B + LoRA | RunPod A100 80GB

---

## 1. 목표

사내 규정 판단 Agent의 LLM을 외부 API(GPT/Claude)에서 **자체 sLLM으로 전환**하여:
- 사내 데이터 외부 유출 차단 (온프레미스 운영)
- 도메인 특화 성능 확보 (규정 판단 정확도 향상)
- 운영 비용 절감 (API 호출 비용 제거)

## 5. 실험 과정 (7회 실험)

### 실험 타임라인

```
v1 하드코딩 3ep (86.6%) ← 최초 학습, 컨텍스트를 직접 포함
    ↓
v2 보강 98건 추가 (83.4%) ← 데이터 추가했으나 오히려 하락 → 폐기
    ↓
v1 RAG 1ep (76.8%) ← 실제 RAG 검색 결과로 컨텍스트 변경 → 대폭 하락
    ↓
v1 RAG 3ep (77.1%) ← epoch 늘려도 개선 미미 → RAG 방식 보류
    ↓
v1 하드코딩 재학습 (83.5%) ← 어댑터 삭제 후 재학습
    ↓
v3 conditional 보강 (84.5%) ← 재량표현 14건 + 경계 5건 추가
    ↓
★ v3 RunPod 재학습 (85.4%) ← A100 80GB에서 최종 학습 → 채택
```

## 6. 핵심 인사이트

### 하드코딩 vs RAG 컨텍스트
- **하드코딩 컨텍스트** (규정 원문 직접 포함)가 RAG 검색 결과보다 10%p 이상 높음
- RAG 검색 결과는 노이즈가 많아 모델이 혼란 → 하드코딩 방식 채택
- 실제 서빙 시에는 RAG로 검색한 규정을 하드코딩 형식으로 정리해서 프롬프트에 삽입

### conditional 카테고리가 가장 어려움
- "조건부 가능"은 판단 경계가 모호 → 재량 표현 데이터 보강으로 개선
- v1(75%) → v3(78%) +3%p 개선

### 데이터 양보다 질
- v2에서 98건 추가했으나 오히려 하락 (83.4%)
- v3에서 19건만 정밀 추가로 +1.9%p 상승 (85.4%)

## 7. 서빙 구조

```
사용자 질문
    ↓
Intent 분류 (BERT 6-label) → judgment
    ↓
RAG 하이브리드 검색 (BM25 + Qdrant + RRF)
    ↓ 관련 규정 Top-K
Judgment Agent
    ↓
┌─────────────────────────────┐
│  sLLM (메인)                │  Fallback
│  Kanana-1.5-8B + LoRA v1   │  GPT-4o-mini / Claude
│  vLLM 서빙 (OpenAI 호환)    │  sLLM 실패 시 자동 전환
└─────────────────────────────┘
    ↓
3중 보조장치 검증
  - 환각 탐지 (RAG에 없는 조항 인용 감지)
  - 조항 존재 검증 (규정 DB 대조)
  - Confidence 보정 (LLM 0.6 + RAG 0.25 + Coverage 0.15)
    ↓
판단 결과 (yes/no/conditional/no_regulation)
+ 근거 조항 + 대안 제시 + 신뢰도
    ↓
SSE 스트리밍 → JudgmentCard UI
```
