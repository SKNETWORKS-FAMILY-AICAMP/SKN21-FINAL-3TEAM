# 판단 Agent 파인튜닝 과정

> 윤경은 (AI Engineer) | Kanana-1.5-8B + LoRA | 7회 실험 | Base 37.2% → 최종 85.4%

---

## 1. 목표

사내 규정 판단 Agent의 LLM을 외부 API(GPT/Claude)에서 **자체 sLLM으로 전환**하여:
- 사내 데이터 외부 유출 차단 (온프레미스 운영)
- 도메인 특화 성능 확보 (규정 판단 정확도 향상)
- 운영 비용 절감 (API 과금 0원)

## 4. Base 모델 성능 (파인튜닝 전)

파인튜닝 전 Kanana-1.5-8B base 모델로 동일한 eval 328건을 평가한 결과:

| 항목 | Base (파인튜닝 전) | v3 최종 (파인튜닝 후) | 개선폭 |
|------|------------------|-------------------|--------|
| **전체 정확도** | **37.2%** | **85.4%** | **+48.2%p** |
| JSON 유효율 | 70.4% | 97.6% | +27.2%p |
| yes | 42% | 86% | +44%p |
| no | 48% | 84% | +36%p |
| conditional | 47% | 78% | +31%p |
| no_regulation | 6% | 97% | **+91%p** |

- Base 모델은 규정 판단 구조(JSON 형식)를 제대로 출력하지 못함 (유효율 70%)
- 특히 no_regulation은 6%로 거의 판별 불가 → 파인튜닝 후 97%로 극복

## 5. 실험 과정 — 한계와 극복

### 실험 요약 (7회)

```
Base 모델 (37.2%) ← 파인튜닝 전 기준점
    ↓
v1 하드코딩 (86.6%) ← 최초 파인튜닝, 규정 원문을 직접 포함 → 큰 폭 개선
    ↓ 한계 1: 데이터를 늘리면 좋아질까?
v2 보강 98건 (83.4%) ← 오히려 하락 → 폐기
    ↓ 한계 2: 실제 RAG로 바꾸면?
v1 RAG (76.8% → 77.1%) ← 10%p 하락 → RAG 노이즈 문제 확인
    ↓ 극복: 하드코딩으로 회귀 + 약점 집중 보강
v3 conditional 보강 (84.5% → 85.4%) ← 19건만 정밀 추가로 최종 채택
```

### 한계 1: 데이터 양을 늘리면 성능이 오를까?

| 실험 | 정확도 | 결과 |
|------|--------|------|
| v1 (2,949건) | 86.6% | 기준점 |
| v2 (+98건 보강) | 83.4% | **-3.2%p 하락** |

- 98건을 추가했지만 오히려 하락
- **원인**: 추가 데이터의 라벨 품질이 낮아 기존 학습을 방해
- **인사이트**: 데이터는 양이 아니라 **질**이 중요

### 한계 2: 하드코딩 컨텍스트를 RAG로 교체하면?

| 실험 | 정확도 | conditional | 비고 |
|------|--------|------------|------|
| v1 하드코딩 | 86.6% | 84% | 규정 원문 직접 포함 |
| v1 RAG 1ep | 76.8% | 62% | RAG 검색 결과 사용 |
| v1 RAG 3ep | 77.1% | 55% | epoch 증가해도 개선 미미 |

- RAG 검색 결과에 **노이즈가 많아** 모델이 혼란
- 특히 conditional 카테고리가 84% → 55%로 급락
- **인사이트**: 학습은 하드코딩, 서빙 시에는 RAG 결과를 **하드코딩 형식으로 정제**하여 삽입

### 한계 3: conditional 카테고리가 가장 어려움

| 버전 | conditional 정확도 |
|------|-----------------|
| v1 하드코딩 재학습 | 75% |
| v3 conditional 보강 | 78% |

- "조건부 가능"은 판단 경계가 모호 (yes와 no 사이)
- **극복**: 재량 표현 14건 + 경계 사례 5건 = **19건만 정밀 추가**
- v2의 98건 실패 vs v3의 19건 성공 → **타겟 보강이 핵심**

---

## 6. 핵심 인사이트 정리

| 인사이트 | 근거 |
|---------|------|
| **데이터 양 < 질** | v2에서 98건 추가 → 하락, v3에서 19건 정밀 추가 → +1.9%p 상승 |
| **하드코딩 > RAG 컨텍스트** | RAG 전환 시 10%p 하락, 서빙 시 RAG 결과를 정제하여 하드코딩 형식으로 삽입 |
| **약점 카테고리 집중 보강** | conditional이 병목 → 재량 표현 + 경계 사례 타겟 보강으로 75% → 78% |
| **Base → LoRA 효과** | 37.2% → 85.4% (+48.2%p), 특히 no_regulation 6% → 97% 극적 개선 |

## 7. 서빙 구조

```
사용자 질문
    ↓
Intent 분류 (ONNX 앙상블) → judgment
    ↓
RAG 하이브리드 검색 (BM25 + Qdrant + RRF + Reranker)
    ↓ 관련 규정 Top-K → 하드코딩 형식으로 정제
Judgment Agent
    ↓
┌─────────────────────────────┐
│  sLLM (메인)                │  Fallback
│  Kanana-1.5-8B + LoRA v1   │  GPT-4o-mini / Claude
│  vLLM 서빙 (OpenAI 호환)    │  sLLM 실패 시 자동 전환
└─────────────────────────────┘
    ↓
3중 보조장치 검증
  - 환각 탐지 (RAG에 없는 조항 인용 감지)
  - 조항 존재 검증 (규정 DB 대조)
  - Confidence 보정 (LLM 0.6 + RAG 0.25 + Coverage 0.15)
    ↓
판단 결과 (yes/no/conditional/no_regulation)
+ 근거 조항 + 대안 제시 + 신뢰도
    ↓
SSE 스트리밍 → JudgmentCard UI
```

## 9. 현재 한계 및 향후 과제

| 한계 | 상세 | 방향 |
