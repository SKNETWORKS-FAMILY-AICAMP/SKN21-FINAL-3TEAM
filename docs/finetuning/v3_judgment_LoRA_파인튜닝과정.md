# 판단 Agent 파인튜닝 과정

> 윤경은 (AI Engineer) | Kanana-1.5-8B + LoRA | 7회 실험 | Base 37.2% → 최종 85.4%

---

## 1. 목표

사내 규정 판단 Agent의 LLM을 외부 API(GPT/Claude)에서 **자체 sLLM으로 전환**하여:
- 사내 데이터 외부 유출 차단 (온프레미스 운영)
- 도메인 특화 성능 확보 (규정 판단 정확도 향상)
- 운영 비용 절감 (API 과금 0원)

---

## 4. Base 모델 성능 (파인튜닝 전)

파인튜닝 전 Kanana-1.5-8B base 모델로 동일한 eval 328건을 평가한 결과:

| 항목 | Base (파인튜닝 전) | v3 최종 (파인튜닝 후) | 개선폭 |
|------|------------------|-------------------|--------|
| **전체 정확도** | **37.2%** | **85.4%** | **+48.2%p** |
| JSON 유효율 | 70.4% | 97.6% | +27.2%p |
| yes | 42% | 86% | +44%p |
| no | 48% | 84% | +36%p |
| conditional | 47% | 78% | +31%p |
| no_regulation | 6% | 97% | **+91%p** |

- Base 모델은 규정 판단 구조(JSON 형식)를 제대로 출력하지 못함 (유효율 70%)
- 특히 no_regulation은 6%로 거의 판별 불가 → 파인튜닝 후 97%로 극복

## 5. 3단계 실험 스토리 — 성공, 실패, 극복

### 37.2% → 85.4% (+48.2%p)

> Base 모델은 규정 판단을 거의 못 함 (37.2%) → LoRA 파인튜닝으로 +48.2%p 끌어올림

---

### 1단계: 성공 — 최초 파인튜닝 (37.2% → 86.6%)

규정 원문을 하드코딩으로 직접 포함한 학습 데이터로 최초 파인튜닝.
- Base 37.2% → **v1 86.6%** (+49.4%p)
- JSON 유효율 70.4% → 98.2%
- no_regulation 6% → 97% (가장 극적 개선)

---

### 2단계: 실패 — 두 가지 시도, 두 가지 실패

**실패 A: 데이터를 늘리면?** — v2 보강 98건 추가

| | 정확도 | 변화 |
|--|--------|------|
| v1 (2,949건) | 86.6% | 기준 |
| v2 (+98건) | 83.4% | **-3.2%p 하락** |

원인: 추가 데이터의 **라벨 품질이 낮아** 기존 학습을 오염시킴

**실패 B: RAG 컨텍스트로 교체하면?** — 실제 검색 결과 사용

| | 정확도 | conditional |
|--|--------|------------|
| v1 하드코딩 | 86.6% | 84% |
| v1 RAG 1ep | 76.8% | 62% |
| v1 RAG 3ep | 77.1% | 55% |

원인: RAG 검색 결과의 **노이즈가 많아** 모델 혼란, epoch 늘려도 개선 안 됨

---

### 3단계: 극복 — 인사이트 반영 (83.5% → 85.4%)

실패에서 얻은 교훈을 적용:

1. **하드코딩 방식으로 회귀** — RAG가 아닌 규정 원문 직접 포함 방식 유지
2. **양이 아닌 질로 보강** — 98건 무작위 추가 대신 **19건만 정밀 타겟 보강**
3. **약점 카테고리 집중** — conditional (판단 경계 모호) 재량 표현 14건 + 경계 사례 5건

| | 정확도 | conditional |
|--|--------|------------|
| v1 하드코딩 재학습 | 83.5% | 75% |
| v3 conditional 보강 | 84.5% | 78% |
| **v3 RunPod 최종** | **85.4%** | **78%** |

서빙 시에는 RAG로 검색한 규정을 **하드코딩 형식으로 정제**하여 프롬프트에 삽입

---

## 6. 핵심 인사이트 3줄

| 인사이트 | 근거 |
|---------|------|
| **데이터 양 < 질** | 98건 무작위 추가 → 하락 / 19건 정밀 추가 → +1.9%p 상승 |
| **하드코딩 > RAG** | RAG 전환 시 10%p 하락 → 학습은 하드코딩, 서빙은 RAG를 정제하여 삽입 |
| **약점 집중 보강** | conditional 병목(75%) → 재량 표현 + 경계 사례 19건 타겟 보강 → 78% |

## 7. 서빙 구조

```
사용자 질문
    ↓
Intent 분류 (ONNX 앙상블) → judgment
    ↓
RAG 하이브리드 검색 (BM25 + Qdrant + RRF + Reranker)
    ↓ 관련 규정 Top-K → 하드코딩 형식으로 정제
Judgment Agent
    ↓
┌─────────────────────────────┐
│  sLLM (메인)                │  Fallback
│  Kanana-1.5-8B + LoRA v1   │  GPT-4o-mini / Claude
│  vLLM 서빙 (OpenAI 호환)    │  sLLM 실패 시 자동 전환
└─────────────────────────────┘
    ↓
3중 보조장치 검증
  - 환각 탐지 (RAG에 없는 조항 인용 감지)
  - 조항 존재 검증 (규정 DB 대조)
  - Confidence 보정 (LLM 0.6 + RAG 0.25 + Coverage 0.15)
    ↓
판단 결과 (yes/no/conditional/no_regulation)
+ 근거 조항 + 대안 제시 + 신뢰도
    ↓
SSE 스트리밍 → JudgmentCard UI
```
