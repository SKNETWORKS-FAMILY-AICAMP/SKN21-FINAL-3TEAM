# 문서 생성 sLLM 파인튜닝 v3 — 학습 데이터 재설계

> GPU: RunPod H200 143GB | 태스크: 문서 생성 (회의록/보고서/제안서) | 모델: Kanana-1.5-8B
> v2 대비 변경: 학습 데이터 재설계 (필드 분포 + 입력 길이 다양화)

---

## 1. v2의 문제점

v2 LoRA 적용 후 QA 테스트에서 핵심 필드 60~86% 빈 배열 문제 발견:

| 문서 유형 | 문제 필드 | v2 채움률 | 원인 |
|----------|----------|:---------:|------|
| 회의록 | decisions | 34% | 학습 데이터에서 랜덤 선택으로 34%만 포함 |
| 회의록 | action_items | 34% | 동일 |
| 보고서 | tasks | 14% | 학습 데이터에서 극히 낮은 포함률 |
| 제안서 | schedule | 25% | 동일 |
| 제안서 | budget | 25% | 동일 |

**근본 원인**: `select_random_fields()`가 content/summary/decisions/action_items를 동일 확률(~34%)로 랜덤 선택 → 모델이 "빈 배열이 기본"으로 학습.

## 2. v3 데이터 재설계

### 2-1. 필드 계층 분리 (3계층)

v2는 core + meta + content(전부 랜덤)이었으나, v3는 **always + priority + content**로 분리:

```
always_content (100% 포함):
  회의록: content, summary
  보고서: overview, main_content
  제안서: content, expected_effect

priority_content (80% 포함):
  회의록: decisions, action_items
  보고서: tasks, next_plan, issues
  제안서: schedule, budget, background, current_situation

content (랜덤):
  나머지 (agenda, risks, notes, achievements 등)
```

### 2-2. 입력 길이 다양화

| 길이 | 비율 | 사용 패턴 |
|------|:----:|----------|
| short (50~200자) | 30% | 폼에서 제목+한줄 메모 |
| mid (200~800자) | 40% | 챗봇 일반 입력 |
| long (800~1500자) | 20% | 상세 기술 |
| xlong (1500~3000자) | 10% | 회의 전체 내용 붙여넣기 |

### 2-3. 할루시네이션 방지 설계

| 방지 수단 | 방법 |
|-----------|------|
| **길이별 sparse 비율** | short 60% / mid 30% / long 20% / xlong 10% |
| **content str 강제** | description에 "서술형 문자열로" 명시 |
| **budget 근거 기반** | "문서에 수치가 있을 때만" |
| **거부 감지** | GPT 거부 메시지 패턴 3회 재시도 |

### 6-5. 핵심 필드 채움률 분석 — 의도된 동작

tasks/schedule/budget의 FT 채움률이 Base 대비 크게 하락한 것처럼 보이지만, **이것은 v3 데이터 설계의 핵심 목표가 달성된 결과**다.

#### 왜 의도된 동작인가

v3 데이터는 **"입력 텍스트에 근거가 있는 필드만 채워라"**를 학습시키기 위해 설계되었다 (2절 참고):

1. **길이별 sparse 비율**: short 입력(50~200자)은 60%가 sparse → 정보가 적은 입력에서 필드를 적게 채우도록 학습
2. **budget 근거 기반**: "문서에 수치가 있을 때만" 채우도록 설계
3. **priority 필드 80% 포함**: 100%가 아닌 이유는 입력에 근거가 없는 케이스를 의도적으로 포함했기 때문

모델은 데이터의 **빈도 분포를 외운 것이 아니라, 입력을 읽고 근거 유무를 판단하는 능력**을 학습했다:

| 필드 | 학습데이터 채움률 | FT 채움률 | 차이 | 해석 |
|------|:--------------:|:--------:|:----:|------|
| tasks | 55.8% | 52.7% | -3.1pp | 입력에 task 근거가 있는 경우만 채움 |
| schedule | 67.8% | 70.7% | +2.9pp | 입력에 일정 근거가 있는 경우만 채움 |
| budget | 43.1% | 46.3% | +3.2pp | 입력에 수치/예산 근거가 있는 경우만 채움 |

#### Base 모델의 94~100% 채움률은 할루시네이션

Base 모델이 tasks 94%, budget 96.6% 채운 것은 **근거 없이 아무 값이나 생성한 것**이다 (False Fill 44.3%). FT 모델은 이를 17.9%로 **59% 감소**시켰다. 이것이 v3 학습의 핵심 성과.

#### 결론

**모델은 설계 의도대로 정상 동작 중.** 채움률 수치만 보면 "하락"처럼 보이지만, v3의 목표는 "모든 필드를 채우는 것"이 아니라 **"근거 있는 필드만 정확히 채우고, 근거 없으면 비우는 것"**이었다. False Fill 44.3% → 17.9% 감소가 이를 증명한다.

#### 참고: 학습데이터 빈 배열 상세

| 필드 | 해당 유형 | 키 존재 | 채워짐 | 빈 배열 `[]` | 이유 |
|------|----------|:------:|:------:|:----------:|------|
| tasks | 보고서(425) | 89.2% | 55.8% | **33.4%** | 입력에 task 정보 없음 |
| schedule | 제안서(506) | 91.9% | 67.8% | **24.1%** | 입력에 일정 정보 없음 |
| budget | 제안서(506) | 91.1% | 43.1% | **48.0%** | 입력에 예산 수치 없음 (AI Hub 원본 특성) |

빈 배열은 boost 스크립트가 키를 추가했으나 입력에 근거가 없어 의도적으로 비워둔 것이다. 이는 데이터 품질 문제가 아니라 **할루시네이션 방지 설계의 일부**.

## 7. v4 실험: 하이퍼파라미터 튜닝 시도 및 한계 확인

v3의 성능을 올리기 위해 v4 실험을 진행했다. 데이터 추가 생성 없이 하이퍼파라미터만 변경.

### 7-1. v4 변경 사항

| 항목 | v3 | v4 | 변경 이유 |
|------|-----|-----|----------|
| LR | 1e-4 | **5e-5** | epoch 2에서 과적합 → 천천히 학습 |
| epochs | 5 | **10** | LR 낮춰서 step 보상 |
| save_steps | epoch | **25** | epoch 1~2 사이 최적점 탐색 |
| early_stopping | 3 | **5** | 느린 수렴 감안 |
| r / alpha | 32 / 64 | 32 / 64 | **유지** (JSON + 근거 판단 두 스킬 학습에 용량 필요) |

### 7-2. v4 학습 결과

- Best checkpoint: **step 275 (epoch 2.95)**, eval_loss = **0.5110** (v3: 0.508)
- Early stopping patience=5 도달로 epoch 4.4에서 학습 종료
- LR 절반 × epoch 두 배 → v3과 동일 지점에 수렴

### 7-3. v4 평가 결과 비교

| 지표 | v3 | v4 | 변화 | 판정 |
|------|-----|-----|------|------|
| JSON 유효율 | 87.3% | **92.0%** | +4.7%p | ✅ 개선 |
| ROUGE-L | 0.665 | **0.704** | +5.9% | ✅ 개선 |
| BERTScore F1 | 0.926 | **0.928** | +0.002 | ✅ 유지 |
| **False Fill율** | **17.9%** | **26.6%** | **+8.7%p** | **❌ 악화** |
| **빈 필드 정확도** | **82.1%** | **73.4%** | **-8.7%p** | **❌ 악화** |

핵심 필드 채움률 변화:

| 필드 | v3 | v4 | 변화 |
|------|-----|-----|------|
| decisions | 87.5% | **100%** | +12.5%p |
| action_items | 92.0% | **100%** | +8.0%p |
| tasks | 52.7% | **80.4%** | +27.7%p |
| schedule | 70.7% | **79.5%** | +8.8%p |
| budget | 46.3% | 46.2% | 동일 |

### 7-4. v4 분석 — ROUGE-L vs False Fill 트레이드오프

v4는 ROUGE-L과 채움률이 올랐지만, **False Fill이 17.9% → 26.6%로 악화**했다.

r=32를 유지하고 LR만 낮춘 결과, 모델이 **"더 많이 채우는" 방향으로 학습**되었다. 채움률은 올랐지만 **근거 없이 채우는 비율도 같이 상승** — v3의 핵심 설계 의도(근거 기반 판단)가 훼손됨.

이는 ROUGE-L과 False Fill 사이에 **트레이드오프**가 존재함을 보여준다:
- 더 많이 채우면 → 정답과 겹치는 내용이 늘어서 ROUGE-L ↑
- 하지만 근거 없는 필드까지 채워서 → False Fill ↑

**실사용 관점에서는 할루시네이션이 적은 v3가 더 안전하다.**

### 7-5. 결론 — v3이 최적

**v4 기각, v3 어댑터 서빙 유지.**

- v3는 "근거 있는 필드만 채우고, 없으면 비운다"를 정확히 학습 (False Fill 17.9%)
- v4는 ROUGE-L이 올랐으나 할루시네이션 증가로 실사용 부적합
- LR을 바꿔도 동일 eval_loss에 수렴 = **데이터/모델이 병목**, 학습 방식으로는 한계
- 추가 실험(r 변경, 다른 LR) 불필요 — 동일 데이터로는 **ROUGE-L ↑와 False Fill ↓를 동시에 달성할 수 없음**
- 더 올리려면 **데이터 추가** 또는 **더 큰 모델**이 필요
