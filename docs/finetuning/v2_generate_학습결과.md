# 문서 생성 sLLM 파인튜닝 보고서

> GPU: RunPod H200 141GB | 태스크: 문서 생성 (회의록/보고서/제안서) | 모델: Kanana-1.5-8B

---

## 1. 문제 정의 — 왜 sLLM이 필요한가

현재 문서 Agent는 GPT-4o API로 문서를 JSON 형식으로 생성한다. 잘 동작하지만 실서비스에 3가지 한계가 있다:

| 문제 | 현재 (GPT-4o API) | 목표 (sLLM 온프레미스) |
|------|:------------------:|:---------------------:|
| **비용** | 호출당 $0.01~0.03, 월 수십 달러 | 고정 서버 비용만 (호출당 추가비용 0) |
| **데이터 보안** | 기업 내부 문서가 외부 서버로 전송 | 자체 서버에서 처리, 외부 유출 없음 |
| **지연시간** | 네트워크 왕복 + API 대기열 | 로컬 추론, 네트워크 지연 없음 |

**해결 방향**: 8B급 오픈소스 모델을 파인튜닝하여 문서 생성 태스크에 특화시키고, 자체 서버(vLLM)로 서빙한다.

## 2. 모델 선정

### 2-1. 왜 8B급인가

| 모델 규모 | GPU 요구 | 서빙 비용 | 성능 |
|:---------:|:--------:|:---------:|:----:|
| 70B+ | A100 80GB × 2+ | 매우 높음 | 최상 |
| 14B | A100 40GB 1장 | 높음 | 상 |
| **8B** | **RTX 4090 24GB** | **낮음** | **중상** |
| 3B 이하 | RTX 3090 | 매우 낮음 | 중하 |

- **RTX 4090 1장**으로 QLoRA 학습 + vLLM 서빙 모두 가능 (비용 효율)
- 3B 이하는 JSON 구조 출력 안정성이 크게 떨어짐
- 14B 이상은 서빙 비용 대비 문서 생성 태스크에서의 개선폭이 크지 않음

### 2-2. 후보 선별 과정 (왜 이 3개인가)

8B급 오픈소스 LLM 중 한국어 문서 생성 태스크에 맞게 2단계로 필터링했다.

**1차 필터: 한국어 사전학습 비중**

| 제외 모델 | 제외 이유 |
|----------|----------|
| Llama 3.1 8B | 영어 중심 학습, 한국어 토큰 비율 극히 낮음 |
| Mistral 7B | 유럽어 중심, 한국어 거의 미지원 |
| Gemma 2 9B | 다국어이나 한국어 비중 작음 |
| Phi-3 | Microsoft, 영어/코드 특화 |

→ 한국어를 **주요 학습 언어**로 포함한 모델만 남김

**2차 필터: 한국어 벤치마크 + 구조화 출력 능력**

| 후보 | 한국어 근거 | 구조화 출력 근거 |
|------|-----------|----------------|
| **Qwen3-8B** | 다국어 학습에 한국어 포함, MMLU-Ko 상위권 | JSON/코드 생성 벤치마크 최상위급 |
| **EXAONE-3.5-7.8B** | LG AI, 한국어 중심 학습, KoMT 7.96 (8B급 최고) | 한국어 Instruction Following 강점 |
| **Kanana-1.5-8B** | Kakao, 한국어 중심 사전학습 | IFEval 80.11, 지시 따르기 강점 |

### 2-3. 후보 3개 모델 상세

| 모델 | 개발사 | 파라미터 | 강점 | 약점 | 라이선스 |
|------|--------|:--------:|------|------|:--------:|
| **Qwen3-8B** | Alibaba | 8.2B | JSON/코드 생성 특화, 14B급 성능 | 한국어 특화 아님, Thinking Mode 간섭 | Apache 2.0 |
| **EXAONE-3.5-7.8B** | LG AI | 7.8B | 한국어 대화 최강 (KoMT 7.96) | **비상업적 라이선스** | 제한적 |
| **Kanana-1.5-8B** | Kakao | 8.0B | 한국어 자연스러움, 한국어 중심 사전학습 | 코드/JSON 사전학습 약함 | Apache 2.0 |

## 3. Base Model 성능 확인 — 파인튜닝의 근거

> 파인튜닝 전에 먼저 base model(파인튜닝 안 한 원본)로 동일한 eval 150건을 평가하여, **"파인튜닝 없이는 실서비스 불가"**라는 근거를 확보했다.

Kanana-1.5-8B base model에 문서 생성 프롬프트를 그대로 넣었을 때:

| 지표 | Base Model (파인튜닝 전) | 목표 |
|------|:------------------------:|:----:|
| JSON 유효율 | (결과 반영 예정) | 98%+ |
| 필드 완성도 | (결과 반영 예정) | 95%+ |
| 필드 정확도 | (결과 반영 예정) | 95%+ |

**예상되는 문제점:**
- JSON 구조를 자주 깨뜨림 (중괄호/따옴표/쉼표 누락)
- 요청한 필드를 누락하거나 엉뚱한 키 이름 사용
- 마크다운, 설명 텍스트 등 JSON 외 불필요한 출력 혼입
- 긴 입력에서 없는 정보를 지어내는 할루시네이션

→ **base model만으로는 문서 생성 서비스가 불가능하다는 것을 확인** → 파인튜닝 필요성 확보

## 4. 학습 데이터

### 데이터 구성

| 항목 | 값 |
|------|-----|
| 총 데이터 | 1,500건 |
| Train / Eval | 1,350건 (90%) / 150건 (10%) |
| 문서 유형 | 회의록 600 + 보고서 450 + 제안서 450 |
| 데이터 소스 | AI Hub 690건 (46%) + 합성 600건 (40%) + 변형 210건 (14%) |

### 데이터 소스별 역할

| 소스 | 비율 | 근거 |
|------|:----:|------|
| **AI Hub** | 46% | 국가 공공 데이터(보고서/간행물) — 실제 문서 패턴 학습 |
| **합성 (GPT-4o/Claude)** | 40% | 공개 기업 회의록 데이터셋이 없음 → 직접 생성 |
| **변형** | 14% | 구어체/오타 변형 → 실사용 패턴 대응력 강화 |

### 데이터 설계 의도

**회의록을 합성으로 만든 이유**: AI Hub 회의록은 국회 속기록(발언자 대화 형식)으로 기업 회의록과 도메인/스타일이 완전히 다르다. 기업 도메인(마케팅, 개발, 인사, 예산 회의 등) 회의록은 공개 데이터셋이 없어 GPT-4o/Claude로 직접 생성했다.

**부분 누락 데이터 (할루시네이션 방지)**: 합성 600건 중 30%(180건)를 의도적으로 일부 필드 없이 생성. 모델이 "정보가 없으면 빈 값을 반환"하는 패턴을 학습하지 않으면, 없는 정보를 지어내서 다른 필드에 채우는 할루시네이션이 발생한다.

## 5. 학습 설정

### QLoRA 설정

| 항목 | 값 | 근거 |
|------|-----|------|
| 양자화 | 4-bit (NF4) | GPU 메모리 절약 (16GB → ~5GB) |
| LoRA r | 32 | 문서 생성은 15+개 필드 JSON 스키마를 학습해야 → 높은 표현력 필요 |
| LoRA alpha | 64 | alpha/r = 2.0 (표준 비율) |
| LoRA dropout | 0.05 | 과적합 방지 |
| Target Modules | q, k, v, o, gate, up_proj | Attention + FFN 전체 (6개 모듈) |

### 학습 설정

| 항목 | 값 | 근거 |
|------|-----|------|
| Epochs | 5 | Eval loss 모니터링으로 early stopping 판단 |
| Batch size | 4 | GPU 메모리 제약 |
| Gradient accumulation | 4 | Effective batch = 16 |
| Learning rate | 1e-4 | QLoRA 표준 학습률 |
| Warmup ratio | 0.1 | 안정적 학습 시작 |
| max_length | 2560 | 데이터 분석 결과 97.8%가 2048 이하, 77건이 최대 2647 → JSON 잘림 방지 |

## 6. 평가 방법

### 왜 JSON 구조 지표인가

문서 생성은 분류(F1/Accuracy)나 번역(BLEU)과 달리 **정답이 여러 개 가능한 태스크**다. 같은 "회의록 작성해줘"에 대해 다양한 표현이 모두 좋은 문서일 수 있다.

| 부적합한 지표 | 부적합 이유 |
|-------------|-----------|
| F1 / Accuracy | 분류 태스크용, 생성에는 적합하지 않음 |
| ROUGE-L | 참조 문장과 표면적 단어 겹침만 측정, 같은 의미의 다른 표현을 패널티 |
| BERTScore | 의미 유사도이지만, 문서 구조 정확성은 측정 불가 |

→ 문서 생성의 핵심은 **"요청한 JSON 구조대로 빠짐없이 출력하는가"**이므로 구조 지표를 사용:

| 지표 | 정의 | 역할 |
|------|------|:----:|
| **JSON 유효율** | 출력이 JSON으로 파싱 가능한 비율 | 핵심 |
| **필드 완성도** | 정답 JSON의 모든 키가 예측에 존재하는 비율 | 핵심 |
| **필드 정확도** | 예측 JSON의 키 이름이 정답과 일치하는 비율 | 핵심 |
| Train/Eval Loss | 학습 수렴 + 과적합 모니터링 | 보조 |

## 8. 최종 모델 선정 — 왜 Kanana인가

### Qwen3-8B 탈락 이유

- JSON 유효율 90.67% (150건 중 14건 파싱 실패) → **서비스 안정성 부족**
- Eval token accuracy는 오히려 최고(0.8094) — 토큰 단위로는 맞추지만 JSON 구조를 깨뜨리는 빈도가 높음
- 원인 추정: Thinking Mode 특성상 JSON 출력 전에 추론 토큰이 섞이면서 구조 파괴

### EXAONE vs Kanana — 핵심 지표 동률에서의 판단

JSON 유효율/필드 완성도가 동일(98.67%)한 상황에서 보조 지표와 실용적 기준으로 판단:

| 비교 항목 | EXAONE | Kanana | 판정 |
|----------|:------:|:------:|:----:|
| Final train loss | 0.5870 | **0.5390** | Kanana |
| Best eval loss | 0.7717 | **0.7257** | Kanana |
| 과적합 경향 | epoch 5에서 +0.0237 | epoch 5에서 +0.0312 | 비슷 |
| 라이선스 | **비상업적 제약** | **Apache 2.0** | Kanana |
| 한국어 품질 | LG AI (한국어 강점) | Kakao (한국어 중심) | 동급 |

**Kanana 선택 근거:**
1. **학습 수렴이 가장 좋다** — final loss 0.5390(최저), eval loss 0.7257(최저)
2. **추후 확장에 유리** — 같은 데이터로 더 잘 배운다 = 데이터 추가 시에도 개선 여지 큼
3. **Apache 2.0 라이선스** — 상업적 사용 제약 없음 (EXAONE은 비상업적 제약)
4. **Kakao 한국어 중심 사전학습** — 한국어 기업 문서 생성에 적합

## 10. 서빙 전략

### LLM API ↔ sLLM 전환 구조

코드 수정 없이 환경변수 하나로 전환:

```
DOC_AGENT_MODE=api   →  GPT-4o API 호출 (기본값)
DOC_AGENT_MODE=sllm  →  vLLM + LoRA 호출 (sLLM 모드)
```

### vLLM 서빙 구성

```bash
python -m vllm.entrypoints.openai.api_server \
  --model kakaocorp/kanana-1.5-8b-instruct-2505 \
  --enable-lora \
  --lora-modules v2_generate=./outputs/v2_generate/kanana-1.5-8b-instruct-2505/final \
  --max-model-len 2560 --dtype bfloat16
```

- GPU: RTX 4090 (24GB) — 8B 모델 + LoRA adapter + KV cache 충분
- 서빙 방식: RunPod GPU Pod (필요 시 켜고 끄기, 시간당 ~$0.44)

## 11. 향후 계획

현재 **문서 생성(generate)**만 완료한 상태. 단계적으로 확장한다:

| 단계 | 내용 | 상태 |
|:----:|------|:----:|
| 1 | v2_generate 파인튜닝 + 모델 선정 | **완료** |
| 2 | Base model eval → 파인튜닝 효과 검증 | **진행 중** |
| 3 | vLLM 서빙 테스트 → 실서비스 연동 확인 | 예정 |
| 4 | generate 실서비스 안정성 확인 후 summary/qa 파인튜닝 | 예정 |
| 5 | GPT-4o vs Fine-tuned Kanana 비교 (sLLM 전환 최종 검증) | 예정 |

**generate를 먼저 한 이유**: 3개 태스크(generate/summary/qa)를 동시에 파인튜닝하면 각각 데이터/평가/디버깅이 필요해 리스크가 크다. generate가 가장 복잡한 태스크(15+필드 JSON)이므로, 이것이 잘 되면 summary/qa는 더 쉽게 적용할 수 있다.
