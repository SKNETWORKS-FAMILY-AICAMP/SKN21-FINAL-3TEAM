# 문서생성 QA 분석 및 개선 계획

> 날짜: 2026-03-16
> 담당: 신지용 (PM)

---

## 배경

회의록 생성 시 `decisions`/`action_items`가 빈 배열로 반환되는 문제가 발생.

### 원인 1: 필드 수 초과 (해결 완료)

- 학습 데이터: 6~10개 필드 (평균 8.1개, 587건 중 99.4%)
- 서비스 코드: DB 시스템 템플릿 13개 필드를 전부 LLM에 전달
- 6개 필드 → BASE/LoRA 모두 정상, 13개 필드 → 둘 다 빈 배열
- **수정**: `GENERATION_FIELD_CONFIG` + `_select_fields_for_llm()` 추가하여 시스템 템플릿 7~10개 필드로 제한
- **검증**: QA 57 PASS / 0 FAIL (2026-03-16)

### 원인 2: 폼 입력과 학습 데이터 형식 불일치 (미해결)

프론트엔드 폼 입력이 학습 데이터의 입력 형식과 다름.

| 항목 | 학습 데이터 | 프론트엔드 입력 |
|------|-----------|----------------|
| 길이 | 500~1500자 (서술형) | ~100~300자 (폼 필드 나열) |
| 형식 | "...회의가 진행되었다. 참석자는..." | "제목: ...\n날짜: ...\n참석자: ..." |
| decisions 정보 | 본문에 "...변경하기로 하였다" 명시 | 언급 없음 |
| action_items 정보 | "...3/19까지 진행하기로 하였다" 명시 | 언급 없음 |

#### 검증 결과

- 폼 형식 입력 (409자 응답) → decisions 0개, action_items 0개
- 서술형 입력 (1416자 응답) → decisions 4개, action_items 4개

## 현재 파이프라인

```
[프론트 입력폼]
  제목, 날짜, 팀, 참석자, 회의내용
       ↓
[백엔드 documents.py]
  폼 필드를 "제목: ...\n날짜: ...\n참석자: ...\n내용" 으로 조립
       ↓
[document_agent.py]
  필드 선별 (13→7개) + 프롬프트 구성
       ↓
[sLLM (LoRA v2_generate)]
  JSON 생성 → decisions, action_items 포함
       ↓
[DOCX 빌더]
  회의록 양식에 맞게 문서 생성
```

**문제 지점**: 백엔드에서 조립하는 user_input 형식이 학습 데이터의 입력 형식과 다름

## 템플릿 구조

### 기본 (시스템) 템플릿
- LLM이 전체 문서를 JSON으로 작성
- 시스템 DOCX 빌더로 문서 생성
- `is_system=True` → 필드 선별 적용

### 커스텀 템플릿
- 사용자가 업로드한 DOCX 양식
- LLM이 필드를 JSON으로 채움
- 원본 양식에 값 삽입 또는 generic 문서 생성
- `is_system=False` → 필드 선별 미적용 (보통 5~8개라 학습 분포 범위 내)

## 개선안

### 1. 백엔드 폼 → 서술형 변환 (우선순위: 높음)

**위치**: `backend/app/api/v1/documents.py` L117~126

폼 입력을 학습 데이터 형식에 맞게 서술형으로 변환:

```
[변환 전 - 현재]
제목: 3팀 주간 스프린트 회의
날짜: 2026-03-16
참석자: 신지용, 윤경은, 진승언
LoRA v2 파인튜닝 완료 보고, vLLM 서빙 이슈 논의

[변환 후]
2026-03-16 3팀 주간 스프린트 회의가 진행되었다.
참석자는 신지용, 윤경은, 진승언이다.
주요 논의 내용은 다음과 같다.
LoRA v2 파인튜닝 완료 보고, vLLM 서빙 이슈 논의
```

- 시스템 프롬프트 변경 없음
- 학습 데이터/재학습 없음
- 프론트엔드 변경 없음
- 회의록(`meeting_minutes`)에만 적용

### 2. 회의내용 placeholder 유도 (우선순위: 높음)

**위치**: `frontend/src/pages/DocumentGeneratePage.jsx`

회의내용 입력란의 placeholder를 유도형으로 변경:
```
"논의 내용, 결정된 사항, 후속 조치를 포함하여 작성해주세요"
```

- 사용자가 결정사항/후속조치를 자연스럽게 입력하도록 유도
- LLM이 추론할 근거가 입력에 포함됨

### 3. 할루시네이션 방지 (현재 상태 유지)

- 시스템 프롬프트: "입력 내용에 해당 정보가 없으면 빈 문자열 또는 빈 배열로 두세요"
- 학습 데이터: 30% 샘플에서 빈 필드 패턴 학습
- decisions/action_items는 OMITTABLE_FIELDS에 포함 → 빈 배열 허용

**판단**: 서술형 변환으로 형식 매칭 + placeholder로 입력 유도하면 충분. 프롬프트에 "반드시 추론하라" 같은 강제 지시는 할루시네이션 리스크 있으므로 추가하지 않음.

## RunPod 서빙 이슈 (2026-03-16 발생)

### 증상
- vLLM 워커 반복 크래시: `cuda>=12.9` 에러

### 원인
- RunPod이 `stable` 태그 뒤의 컨테이너 이미지를 CUDA 12.9 기반으로 업데이트
- 배치된 노드의 드라이버가 12.9 미만

### 해결
- Docker Image: `registry.runpod.net/...` (기존 유지)
- Minimum CUDA: `12.9`로 변경 → 12.9 이상 드라이버 노드에만 배치

### 교훈
- RunPod 플로팅 태그(`stable`, `latest`)는 예고 없이 업데이트될 수 있음
- 안정 운영 시 고정 태그 사용 권장
